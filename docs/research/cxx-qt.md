# What cxx-qt can and cannot do today

Research for ticket #3, part of the native line map (#2). Written 2026-09-03 against cxx-qt 0.10.0, Qt 6.11.1 and Rust 1.92.0 on the owner's Arch desktop. Vocabulary follows CONTEXT.md: the core is the Rust crate, the shell is the Qt app, the bridge is the cxx-qt layer between them, calls go shell to core, events go core to shell, and a job is long work that reports through events.

## Summary

1. Use cxx-qt 0.10.0 (released 2026-08-24, MSRV 1.85). It builds and runs against Qt 6.11.1 with Rust 1.92 and GCC 16 on this box; KDAB's own CI stops at Qt 6.10.1 and nothing upstream mentions 6.11, so that build is our evidence, not theirs.
2. Cargo alone builds the Linux shell. One build.rs registers the QML module, bundles qrc files, runs moc, rcc, qmlcachegen and qmltyperegistrar, compiles shim C++ and links the pacman Qt through qmake6. No CMake. The PKGBUILD needs rust, qt6-base, qt6-declarative and lld at build time, qt6-base and qt6-declarative at run time.
3. The core's bridge object is one Rust QObject marked `#[qml_singleton]`; the QML engine constructs and owns it. Calls are `#[qinvokable]` methods that return at once; events reach QML as Qt signals.
4. Events cross from tokio threads through `CxxQtThread::queue`, a Clone, Send and Sync handle that posts a queued invocation to the Qt thread and returns an error instead of crashing once the object is gone. Each queue call allocates twice and takes a shared lock, so a job batches its progress rather than queueing per file.
5. Invokables cannot be async. The maintainers' pattern is `#[tokio::main]` around `QGuiApplication`, `tokio::spawn` inside the invokable, `queue` on the way back. That is the synchronous facade the map already decided on.
6. Rust enums with fields do not cross the bridge: `#[qenum]` allows unit variants only and there is no Q_GADGET. The bridge object therefore exposes one invokable per call variant and one Qt signal per event kind with flat cxx-typed arguments, or a `QJsonObject` payload, and builds the core's call and event values on the Rust side.
7. List models work in Rust: `#[base = QAbstractListModel]` with `data`, `rowCount` and `roleNames` overridden, roles as a `#[qenum]`, `beginInsertRows` and friends reached through `#[inherit]`. cxx-qt ships no safe wrapper on purpose; write a Drop guard for the begin/end pairs.
8. What crosses as values: QString, QUrl, QVariant, QList<T> for a fixed list of T, QStringList, QVariantMap as `QMap<QString, QVariant>`, QVariantList, and since 0.10.0 QJsonArray, QJsonObject and QJsonValue. Every container instantiation needs its own alias line in the bridge.
9. A QQuickItem can be subclassed from Rust: an official example overrides `QQuickPaintedItem::paint`, and a KDAB Labs demo overrides `QQuickFramebufferObject::createRenderer` plus `Renderer::render` and `synchronize`. cxx-qt-lib has no QQuickItem, QSGNode or OpenGL types, so the video surface keeps a small C++ header of helpers whichever route the mpv spike picks.
10. The risks to plan for: the API is pre-1.0 and moves every minor; Qt 6.9.2 broke code generation for three and a half weeks and Arch users hit it first; a panic inside any bridge function aborts the process; dynamic QML plugins are CMake-only, so the shell uses the default static module.

## 1. Current release and Qt 6.11 support

The newest release is 0.10.0 on 2026-08-24, after 0.9.1 (2026-07-03), 0.9.0 (2026-06-23), 0.8.1 (2026-02-16) and 0.8.0 (2025-12-18) (https://github.com/KDAB/cxx-qt/blob/main/CHANGELOG.md, https://github.com/KDAB/cxx-qt/releases). 0.10.0 added QJsonArray, QJsonObject and QJsonValue, the ItemFlag and ItemDataRole enums, and `*mut QObject` inside QList and QVariant (same CHANGELOG). The Unreleased section is empty as of this writing.

The workspace declares `rust-version = "1.85.0"` and depends on cxx 1.0.176 (https://github.com/KDAB/cxx-qt/blob/main/Cargo.toml); crates.io reports rust_version 1.85.0 for 0.9.0, 0.9.1 and 0.10.0 (https://crates.io/api/v1/crates/cxx-qt). CI pins `rustup default 1.85.0` (https://github.com/KDAB/cxx-qt/blob/main/.github/workflows/github-cxx-qt-tests.yml). Rust 1.92 is above that floor. This box runs rustc 1.92.0 from rustup (local `rustc --version`); the Arch repository package is at 1.98.0 (https://archlinux.org/packages/extra/x86_64/rust/), so the ticket's 1.92 is the rustup toolchain, not pacman's.

Qt support as stated by the project: "We currently aim to support the Qt versions that have official support by the Qt company", listed as Qt 5.15 LTS and "All versions of Qt 6"; older is "explicitly unsupported" (https://github.com/KDAB/cxx-qt/blob/main/README.md). The same README says "CXX-Qt is in early development and the API changes frequently".

What CI tests: Qt 5.15.2, 6.2.4, 6.7.3 and 6.10.1 on ubuntu-24.04, macos-15 and windows-2022, installed through aqtinstall (workflow file above). The matrix moved from 6.9.3 to 6.10.1 on 2025-12-17 (https://github.com/KDAB/cxx-qt/commit/e0608cba) and has not moved since; later commits to the workflow are dependency bumps. GitHub search finds no issue, pull request or commit in the repo mentioning 6.11 (`gh search issues`, `gh search prs`, `gh api search/commits`, all empty on 2026-09-03). The Qt version gates in cxx-qt-lib's C++ check for 6.0, 6.7 and 6.8 only; nothing is conditional on 6.9 or later (`gh search code --repo KDAB/cxx-qt QT_VERSION_CHECK`).

Evidence that 6.11 works anyway. Issue #1454 is an Arch user on Qt 6.11.1 whose Cargo build could not find Qt because only `qmake6` was on PATH; it closed on 2026-07-03 when 0.9.1 shipped the fix "Fix finding qmake in PATH when only qmake6 is available and no qmake" (https://github.com/KDAB/cxx-qt/issues/1454, CHANGELOG 0.9.1). A NixOS 26.05 user built cxx-qt from git against Qt 6.11.1 on 2026-08-23 after pointing `QMAKE` at the right binary (comment on https://github.com/KDAB/cxx-qt/issues/1153).

Verified on this box, 2026-09-03: the v0.10.0 source tarball's Cargo-only example (`cargo build -p qml-minimal-no-cmake`, the crate at https://github.com/KDAB/cxx-qt/tree/main/examples/cargo_without_cmake) compiled from scratch in 1m 53s with exit 0 against qt6-base 6.11.1-1, qt6-declarative 6.11.1-3, rustc 1.92.0 and GCC 16.1.1. The binary links /usr/lib/libQt6Core.so.6, libQt6Gui.so.6, libQt6Qml.so.6 and libQt6Network.so.6 (`ldd`), and ran for five seconds under `QT_QPA_PLATFORM=offscreen` with no output, so its QML module loaded. The build printed 1663 C++ warnings from cxx-qt-lib, all GCC 16's new `-Wsfinae-incomplete` against Qt's own headers; none were errors.

The precedent to plan around: Qt 6.9.2 changed how moc declares enums and every `#[qenum]` stopped compiling. An Arch user reported it on 2025-09-07 after a system update; the maintainers advised staying on 6.9.1; the fix merged and shipped as 0.7.3 on 2025-10-02 (https://github.com/KDAB/cxx-qt/issues/1328, https://github.com/KDAB/cxx-qt/releases/tag/v0.7.3). Arch's repositories are already at qt6-base 6.11.2-3 (2026-08-28) and qt6-declarative 6.11.2-1 (https://archlinux.org/packages/extra/x86_64/qt6-base/, https://archlinux.org/packages/extra/x86_64/qt6-declarative/), one `pacman -Syu` ahead of this box, and nobody I could find has built cxx-qt against 6.11.2. Pin cxx-qt to an exact version in Cargo.toml and treat a Qt point release as a reason to rebuild the shell before upgrading.

## 2. Cargo-only builds through cxx-qt-build

The book's Cargo chapter states "Cargo will do the entire build, including linking to Qt, just like a typical Rust application" and ends with `cargo run` (https://kdab.github.io/cxx-qt/book/getting-started/4-cargo-executable.html). The prerequisites page requires Qt 5 or 6 and says a `qmake` on PATH is "vital" (https://kdab.github.io/cxx-qt/book/getting-started/index.html). The CMake 3.24 requirement on that page applies to the CMake route only. The whole build script of the maintained example is one chain: `CxxQtBuilder::new_qml_module(QmlModule::new("com.kdab.cxx_qt.demo").qml_file("qml/main.qml")).qt_module("Network").files(["src/cxxqt_object.rs"]).build()` (https://github.com/KDAB/cxx-qt/blob/main/examples/cargo_without_cmake/build.rs). The build API was reshaped in 0.8.0, so 0.7-era material on the web is stale (CHANGELOG 0.8.0).

### QML modules

`QmlModule::new(uri)` takes `version(major, minor)` (default 1.0), `qml_file` and `qml_files`, `depend` and `depends`, and `plugin_type` (default static) (https://docs.rs/cxx-qt-build/latest/cxx_qt_build/struct.QmlModule.html). The QML files "are registered with the Qt Resource System in the default QML import path `qrc:/qt/qml/uri/of/module/`" and "This will automatically add the `Qml` Qt module to the build" (https://docs.rs/cxx-qt-build/latest/cxx_qt_build/struct.CxxQtBuilder.html#method.new_qml_module). The example loads `qrc:/qt/qml/com/kdab/cxx_qt/demo/qml/main.qml` (https://github.com/KDAB/cxx-qt/blob/main/examples/cargo_without_cmake/src/main.rs). Under the hood the build writes a qmldir, writes and compiles a qrc, runs qmlcachegen on Qt 6, runs qmltyperegistrar on moc's metatypes JSON and generates a `QQmlEngineExtensionPlugin` (https://github.com/KDAB/cxx-qt/blob/main/crates/qt-build-utils/src/lib.rs). Since 0.8.0 one `CxxQtBuilder` holds one QML module, and Rust files go through `files`, not the module (CHANGELOG 0.8.0). The build exports qmldir and qmltypes to `target/cxxqt/qml_modules` for qmllint and writes a `.qmlls.ini` next to Cargo.toml (https://kdab.github.io/cxx-qt/book/concepts/build_systems.html).

Dynamic QML plugins are "with CMake only" (build_systems page above); the `plugin_type` docs say Cargo cannot produce the plugin file layout and to prefer static modules (https://github.com/KDAB/cxx-qt/blob/main/crates/cxx-qt-build/src/qml_modules.rs). Issue #1433, the most active open issue (25 comments, opened 2026-03-21), shows why: a cdylib plugin drops the `qt_plugin_instance` symbol, the maintainer traces it to a rustc limitation on re-exporting C symbols from a cdylib and offers a linker version script as the only workaround (https://github.com/KDAB/cxx-qt/issues/1433). The shell is one executable with a static module, so this does not touch us.

### qrc resources

`.qrc("path.qrc")` takes a hand-written file and `.qrc_resources(["images/a.png", ...])` takes a list; with a QML module set, unprefixed resources land under `/qt/qml/<uri>/` (https://docs.rs/cxx-qt-build/latest/cxx_qt_build/struct.CxxQtBuilder.html#method.qrc, and `#method.qrc_resources`). cxx-qt-build writes the generated qrc files and runs Qt's rcc on every one, using `rcc --list` to emit rerun-if-changed lines (https://github.com/KDAB/cxx-qt/blob/main/crates/cxx-qt-build/src/lib.rs); a missing rcc panics with "Could not find rcc" (https://github.com/KDAB/cxx-qt/blob/main/crates/qt-build-utils/src/tool/rcc.rs). The qml_features example uses both forms (https://github.com/KDAB/cxx-qt/blob/main/examples/qml_features/rust/build.rs).

### C++ sources in the same build

`.cpp_file(...)` and `.cpp_files([...])` exist to "allow building QObject C++ subclasses besides the ones autogenerated by cxx-qt"; headers get moc and are not compiled, other files are compiled without moc, both overridable per file (https://docs.rs/cxx-qt-build/latest/cxx_qt_build/struct.CxxQtBuilder.html#method.cpp_file, https://github.com/KDAB/cxx-qt/blob/main/crates/cxx-qt-build/src/cpp_file.rs). Include paths come from `.include_dir(dir)`, `.crate_include_root(...)` and `.include_prefix(...)` (same docs.rs page). Anything else goes through `cc_builder`, which hands out the internal `cc::Build`; 0.8.0 made it `unsafe` "to indicate its lack of guarantees" (CHANGELOG 0.8.0). qml_features compiles `custom_object.cpp` and `external_qobject.cpp` this way with `.include_dir("../cpp")` (qml_features build.rs above). Qt modules are named without the prefix, `.qt_module("Quick")`; Core is always linked and modules from dependencies propagate (https://docs.rs/cxx-qt-build/latest/cxx_qt_build/struct.CxxQtBuilder.html#method.qt_module). Gui and Qml also arrive through cxx-qt-lib's `qt_gui` and `qt_qml` features; `qt_full` bundles those with `qt_quickcontrols` (https://github.com/KDAB/cxx-qt/blob/main/crates/cxx-qt-lib/Cargo.toml).

### Finding and linking the system Qt

Discovery order: the `QMAKE` environment variable, else `qmake6`, `qmake-qt5`, `qmake` on PATH, each validated with `qmake -query QT_VERSION` and matched against `QT_VERSION_MAJOR` when set (https://github.com/KDAB/cxx-qt/blob/main/crates/qt-build-utils/src/installation/qmake.rs). The `qmake6` step is the 0.9.1 fix from #1454 above; on 0.9.0 or older, Arch needs `QMAKE=/usr/bin/qmake6`. There is no pkg-config or CMake path; issue #1153 (open) documents that split installs such as Nix and Craft defeat the qmake query and that `QMAKE` is the workaround (https://github.com/KDAB/cxx-qt/issues/1153). Arch is not split: on this box `qmake6 -query` reports `QT_INSTALL_PREFIX:/usr`, `QT_INSTALL_HEADERS:/usr/include/qt6`, `QT_INSTALL_LIBS:/usr/lib`, `QT_INSTALL_QML:/usr/lib/qt6/qml`, `QT_INSTALL_LIBEXECS:/usr/lib/qt6`, `QT_VERSION:6.11.1` (local check).

Linking emits `rustc-link-search` for `QT_INSTALL_LIBS` and `rustc-link-lib=Qt6<Module>` per module, then reads `libQt6<Module>.prl` for transitive libraries and panics "Could not find a prl path for Qt module" when the .prl is missing (https://github.com/KDAB/cxx-qt/blob/main/crates/qt-build-utils/src/installation/shared.rs). No link kind is given, so Cargo links dynamically; static linking needs a static Qt and is tracked in #1102 (https://github.com/KDAB/cxx-qt/issues/1102). The `link_qt_object_files` feature the book asks for "makes no difference" when Qt is dynamic (https://github.com/KDAB/cxx-qt/blob/main/crates/qt-build-utils/Cargo.toml). No rpath is set on Linux; #224 has been open since 2022 and the workaround is `LD_LIBRARY_PATH` (https://github.com/KDAB/cxx-qt/issues/224). With Qt in /usr/lib that never bites.

The linker matters. `QtPlatformLinker::init()` runs in every build; when the system `ld` is GNU bfd it adds `-fuse-ld=lld`, else gold, else mold, and warns "Linking with GNU ld.bfd will likely fail" if none is present (https://github.com/KDAB/cxx-qt/blob/main/crates/qt-build-utils/src/platform.rs). This box has GNU ld 2.47 as `ld` and lld 22.1.8 installed, so lld is what linked the test build (local `ld --version`, `pacman -Q lld`). The PKGBUILD lists `lld` in makedepends.

New in 0.9.0, "Qt Minimal": with the `qt_minimal` feature on qt-build-utils, the build "will first check for a system Qt install matching the Qt version requirements first and then download Qt minimal if required"; it "does not provide all Qt features or modules and is primarily designed for Qt QML usage" (https://kdab.github.io/cxx-qt/book/getting-started/6-cargo-qt-minimal.html). The shell leaves that feature off and uses pacman's Qt.

### Tools the build runs

moc runs on every generated bridge header, every `cpp_file` header and the plugin; rcc on every qrc; qmltyperegistrar on the moc JSON; qmlcachegen per QML file on Qt 6 (qt-build-utils lib.rs and cxx-qt-build lib.rs above). Tools are located through `qmake -query` on `QT_HOST_LIBEXECS`, `QT_HOST_BINS` and their install variants, and a missing tool panics with "Could not find moc" or the like (https://github.com/KDAB/cxx-qt/blob/main/crates/qt-build-utils/src/tool/mod.rs). On Arch, `/usr/lib/qt6/moc` and `rcc` belong to qt6-base and `/usr/lib/qt6/qmltyperegistrar` and `qmlcachegen` to qt6-declarative; the QtQuick, QtQuick.Controls, QtQuick.Templates and QtQuick.Layouts QML modules under `/usr/lib/qt6/qml` also belong to qt6-declarative (local `pacman -Qo`). Issue #530 (open) shows the confusing errors when those runtime modules are absent (https://github.com/KDAB/cxx-qt/issues/530).

### Initialisers and multi-crate layouts

Each crate's and module's registration is wrapped in an `extern "C" cxx_qt_init_crate_<name>` or `cxx_qt_init_qml_module_<uri>` function, linked through a tiny whole-archive library so the linker keeps it (https://kdab.github.io/cxx-qt/book/internals/build-system.html). A single-crate app needs no manual call; the example main has none. When a dependency crate provides a QML module the Rust code never references, the link fails with "undefined reference to 'cxx_qt_init_qml_module_...'"; fix one is `extern crate another_crate;`, fix two for older linkers is `cxx_qt::init_crate!` and `cxx_qt::init_qml_module!` in `main`, tests and doc-tests (https://kdab.github.io/cxx-qt/book/common-issues.html). Library crates with bridges set Cargo's `links` key and call `.build().export()` (https://github.com/KDAB/cxx-qt/blob/main/crates/cxx-qt-build/src/interface.rs). Since the core stays a plain Rust crate and only the shell crate holds bridges, this only matters if the bridge is split out later. Integration tests under `tests/` in a Cargo-only layout fail to link (#770, open, https://github.com/KDAB/cxx-qt/issues/770); test the core in its own crate and keep bridge tests to what `cargo test` in the shell can reach.

## 3. QObject features from Rust

Every claim here is for 0.10.0; the bridge is a `#[cxx_qt::bridge]` module holding `extern "RustQt"` blocks for Rust-defined objects, `extern "C++Qt"` blocks for existing Qt objects, and plain cxx blocks for types (https://kdab.github.io/cxx-qt/book/bridge/extern_rustqt.html, https://kdab.github.io/cxx-qt/book/bridge/extern_cppqt.html).

### Properties

`#[qproperty(TYPE, NAME)]` on the `#[qobject]` alias generates getter, setter and a `NAME_changed` signal; flags `READ`, `WRITE`, `NOTIFY`, `CONSTANT`, `REQUIRED`, `FINAL` and `RESET`, each with an optional custom function, arrived in 0.7.0 along with the move from struct field to alias (extern_rustqt page above, CHANGELOG 0.7.0). `READ` alone gives a read-only property. Property types are any type cxx can pass (https://kdab.github.io/cxx-qt/book/concepts/types.html); the examples use bool, i32, QString, QUrl, QPointF, `QMap<QString, QVariant>`, a `#[qenum]` and `*mut InnerObject` (https://github.com/KDAB/cxx-qt/blob/main/examples/qml_features/rust/src/properties.rs, .../containers.rs, .../nested_qobjects.rs). If code mutates the field through `rust_mut()`, it must emit the changed signal itself; the containers example does (containers.rs above). Setters compare old and new values and skip the notify when equal, which is issue #1000's complaint (https://github.com/KDAB/cxx-qt/issues/1000).

### Invokables

`#[qinvokable]` on a function in `extern "RustQt"` with `self: &T` or `self: Pin<&mut T>`; the body is a normal `impl qobject::T` method (extern_rustqt page; https://github.com/KDAB/cxx-qt/blob/main/examples/qml_features/rust/src/invokables.rs). Arguments and returns follow cxx rules, including `Result<T>` (https://github.com/KDAB/cxx-qt/blob/main/crates/cxx-qt-gen/test_inputs/invokables.rs). A `#[qenum]` is a valid argument; a `*mut QObjectType` argument makes the function `unsafe` (https://kdab.github.io/cxx-qt/book/concepts/nested_objects.html). Async invokables do not exist. The maintainer's answer in discussion #805: with `main` in Rust, `#[tokio::main]` around `QGuiApplication::new()` works, `tokio::spawn` inside invokables works, and results come back through `CxxQtThread`; cxx-async and a `QFuture` return type are "yet to explore" (https://github.com/KDAB/cxx-qt/discussions/805). The shipped threading demo uses `async-std` workers driven by `block_on` on `std::thread` (https://github.com/KDAB/cxx-qt/blob/main/examples/demo_threading/rust/src/lib.rs).

### Signals

`#[qsignal] fn name(self: Pin<&mut T>, args...)` with no body; calling it emits (extern_rustqt page; https://github.com/KDAB/cxx-qt/blob/main/examples/qml_features/rust/src/signals.rs). Arguments seen in official sources: i32, QString, QPoint by value, `&QUrl`, `&QModelIndex`, `&QVector_i32`, `UniquePtr<Opaque>` and `*mut InnerObject` (signals.rs, custom_base_class.rs, nested_qobjects.rs, https://github.com/KDAB/cxx-qt/blob/main/crates/cxx-qt-gen/test_inputs/signals.rs). A QObject travels as a raw pointer, the same way C++ hands one to QML (https://github.com/KDAB/cxx-qt/issues/1118). Rust connects with the generated `on_<signal>(|qobject, args| ...)` or `connect_<signal>(handler, ConnectionType)`; both return a `QMetaObjectConnectionGuard` that disconnects on drop, and `.release()` hands back the bare connection (extern_rustqt page; CHANGELOG 0.7.0). The 2025 guard was unsound under `mem::forget` and was fixed in a semver-breaking change (https://github.com/KDAB/cxx-qt/issues/1336). `ConnectionType` offers Auto, Direct, Queued and BlockingQueued; "UniqueConnection is not supported" (https://docs.rs/cxx-qt/latest/cxx_qt/struct.ConnectionType.html). QML sees a signal on a `#[qml_element]` as a normal handler (https://github.com/KDAB/cxx-qt/blob/main/examples/qml_features/qml/pages/SignalsPage.qml). Emitting consumes the `Pin`, so emitting twice needs `self.as_mut()` each time, which the maintainers call boilerplate they would like to remove (https://github.com/KDAB/cxx-qt/issues/728). Base class signals such as `dataChanged` are declared with `#[inherit] #[qsignal]` (https://github.com/KDAB/cxx-qt/blob/main/examples/qml_features/rust/src/custom_base_class.rs). Signals cannot connect directly to another QObject's slot, only to closures (#1200, open, https://github.com/KDAB/cxx-qt/issues/1200).

### Threading, the path an event takes from tokio to QML

Per object, `impl cxx_qt::Threading for T {}` in the bridge gives `self.qt_thread()`, returning `CxxQtThread<T>` (https://github.com/KDAB/cxx-qt/blob/main/examples/qml_features/rust/src/threading.rs, https://docs.rs/cxx-qt/latest/cxx_qt/trait.Threading.html). Generated QObjects are neither Send nor Sync; the thread handle is (same page). `queue<F>(&self, f: F) -> Result<(), ThreadingQueueError> where F: FnOnce(Pin<&mut T>) + Send + 'static` (https://docs.rs/cxx-qt/latest/cxx_qt/struct.CxxQtThread.html). The handle is `Clone`, `Send` and `Sync` by explicit unsafe impls in the source, so a tokio task can hold a clone for the life of the runtime (https://github.com/KDAB/cxx-qt/blob/main/crates/cxx-qt/src/threading.rs). On the C++ side the handle owns a `shared_ptr` to a guarded pointer with a `shared_mutex`; `queue` takes a shared lock, returns `ObjectDestroyed` when the pointer is null, otherwise posts a lambda with `QMetaObject::invokeMethod(ptr, lambda, Qt::QueuedConnection)`; when the lambda runs on the Qt thread it re-locks and, if the object died meanwhile, prints "Could not call the function pointer as object has been destroyed" and skips (https://github.com/KDAB/cxx-qt/blob/main/crates/cxx-qt/include/thread.h). The error enum has `ObjectDestroyed`, `InvokeMethodFailed` and `Unknown` (https://docs.rs/cxx-qt/latest/cxx_qt/enum.ThreadingQueueError.html); the docs warn that `is_destroyed()` races with `queue` and recommend `queue(...).ok()` (CxxQtThread page above).

Cost per queue call: the generated Rust boxes the closure twice (https://github.com/KDAB/cxx-qt/blob/main/crates/cxx-qt-gen/src/generator/rust/threading.rs) and C++ copies a `shared_ptr` and takes the shared lock (thread.h above). No document states a limit; #595 set out to reduce "so much heap-allocation and wrapping" (https://github.com/KDAB/cxx-qt/issues/595). For a scan or match sweep, the job coalesces progress into one queued call per tick, not one per file.

Threading is only available on `extern "RustQt"` objects; extending it to imported QObjects is open #1155 (https://github.com/KDAB/cxx-qt/issues/1155). No Qt-side future or async type exists in cxx-qt-lib (https://docs.rs/cxx-qt-lib/latest/cxx_qt_lib/).

### Enums

`#[qenum(MyObject)]` produces `Q_ENUM` on that object; a namespaced `#[qenum]` with `qnamespace!` produces `Q_ENUM_NS`; the object must be a `#[qobject]` in an `extern "RustQt"` block of the same bridge (https://kdab.github.io/cxx-qt/book/bridge/shared_types.html). The parser rejects `#[repr]`, tuple or struct variants, and explicit discriminants ("QEnum variants with explicit values are not supported (yet)") (https://github.com/KDAB/cxx-qt/blob/main/crates/cxx-qt-gen/src/parser/qenum.rs). In Rust the enum is cxx's shared enum, a struct with a `repr: i32` field, matched with a `_` fallback (custom_base_class.rs above, https://cxx.rs/shared.html). An enum works as a property and as an invokable argument (custom_base_class.rs, invokables.rs).

### Type mapping

cxx-qt-lib 0.10.0 ships, ungated: QString, QByteArray, QStringList, QVariant, QDate, QTime, QDateTime, QTimeZone, QPoint(F), QRect(F), QSize(F), QLine(F), QMargins(F), QUrl, QUuid, QList, QVector, QMap, QHash, QSet, QModelIndex, QPersistentModelIndex, QCoreApplication, QJsonArray, QJsonObject, QJsonValue, QtLogging. Behind `qt_gui`: QColor, QFont, QImage, QPainter, QPainterPath, QPen, QPolygon(F), QRegion, QVector2D/3D/4D, QQuaternion, QGenericMatrix, QGuiApplication. Behind `qt_qml`: QQmlEngine, QQmlApplicationEngine, QQmlImageProviderBase. Behind `qt_quickcontrols`: QQuickStyle (https://github.com/KDAB/cxx-qt/tree/main/crates/cxx-qt-lib/src, https://docs.rs/cxx-qt-lib/latest/cxx_qt_lib/). Conversion features `serde`, `chrono`, `time`, `url`, `uuid`, `rgb`, `bytes`, `http` and `image` are all off by default; `full` turns everything on (https://docs.rs/crate/cxx-qt-lib/latest/features).

`QList<T>` and `QVector<T>` accept bool, the float and integer primitives, QByteArray, QColor, QDate, QDateTime, QLine(F), QMargins(F), QPersistentModelIndex, QPoint(F), QRect(F), QSize(F), QString, QTime, QUrl, QUuid and QVariant, plus `QObjectMutPtr` for QList; any other T needs a `QListElement` impl and a C++ instantiation (https://docs.rs/cxx-qt-lib/latest/cxx_qt_lib/struct.QList.html). `QList<QModelIndex>` is one such gap, open since 2026-07-14 (https://github.com/KDAB/cxx-qt/issues/1468). QMap ships one pair, QString to QVariant; QHash ships QString to QVariant and i32 to QByteArray (https://github.com/KDAB/cxx-qt/tree/main/crates/cxx-qt-lib/src/core/qmap, .../qhash). Replacing the pair aliases with `QHash<K, V>` is a 1.0 item (https://github.com/KDAB/cxx-qt/issues/1138). Every container instantiation needs an alias in the bridge, `type QList_i32 = cxx_qt_lib::QList<i32>;` with its `include!` (containers.rs above, types page above).

QVariantMap is `QMap<QString, QVariant>` and QML sees it as a map; the containers example exposes one as a property (types page, containers.rs). QVariantList is `QList<QVariant>`, which implements `QVariantValue` since 0.10.0 (https://docs.rs/cxx-qt-lib/latest/cxx_qt_lib/trait.QVariantValue.html, CHANGELOG 0.10.0). `QVariant::from(&T)` and `value::<T>()` cover the primitives, the core and gui types, QStringList, QModelIndex, `*mut QObject`, the two string-keyed maps and the listed QList types (https://docs.rs/cxx-qt-lib/latest/cxx_qt_lib/struct.QVariant.html). Putting a Rust struct into a QVariant needs a `#[repr(C)]` `ExternType`, a C++ header that defines it and a `canConvert` helper; the types example shows all three (https://github.com/KDAB/cxx-qt/blob/main/examples/qml_features/rust/src/types.rs). Q_GADGET generation does not exist; the exploration issue has been open since 2022 (https://github.com/KDAB/cxx-qt/issues/352).

### What crosses and what needs a shim

Crosses with no C++: properties, invokables and signals over cxx-compatible types; the cxx-qt-lib types above; unit-variant enums; QObject pointers; subclassing any QObject-derived class declared in `extern "C++Qt"`, including overrides and calls into the base.

Needs a C++ header: a Rust struct as a value type (write the Q_GADGET in C++ and bind it, or send a QVariantMap or QJsonObject instead); a custom T inside QList, QSet, QHash, QMap or QVariant; constructors for existing Qt classes bound through `extern "C++Qt"`, which "you currently would need to write constructors manually" (https://github.com/KDAB/cxx-qt/issues/1176); nested class names and template instantiations that cxx cannot spell (section 4). Creating a Rust QObject from Rust uses cxx-qt-lib's `make_unique`, `make_shared` and `new_ptr` helpers declared in the bridge, "Not the same as `std::make_unique`" (https://kdab.github.io/cxx-qt/book/concepts/instantiating_in_rust.html).

Consequence for the contract: a call is an enum with fields and an event is a fact with a payload, and neither shape crosses the bridge as itself. The bridge object exposes one invokable per call variant and one Qt signal per event kind, with flat arguments drawn from the type list, or carries the payload as a QJsonObject. It constructs the core's call and event values on the Rust side of the bridge; the core never sees a Qt type.

## 4. QQuickItem and QQuickFramebufferObject from Rust

A Rust QObject may name any QObject-derived base: `#[base = T]` on the alias, where T is declared in an `unsafe extern "C++"` or `extern "C++Qt"` block with the Qt header included; there is no fixed list of allowed bases (https://kdab.github.io/cxx-qt/book/bridge/extern_rustqt.html#base-attribute, https://kdab.github.io/cxx-qt/book/concepts/inheritance.html). Since 0.7.0 the attribute takes an identifier, not a string; since 0.8.0 up and down casting is generated for anything with `#[base]` (CHANGELOG). Virtuals are overridden with `#[cxx_override]`, added with `#[cxx_virtual]`, sealed with `#[cxx_final]`, and since 0.8.0 declared pure with `#[cxx_pure]` (https://kdab.github.io/cxx-qt/book/bridge/extern_rustqt.html#specifiers). Base methods, including protected ones, are reached with `#[inherit]`, which generates a public forwarding template on the subclass (https://github.com/KDAB/cxx-qt/blob/main/crates/cxx-qt-gen/test_outputs/inheritance.h). Every generated override is `noexcept` (https://github.com/KDAB/cxx-qt/blob/main/crates/cxx-qt-gen/src/generator/cpp/method.rs).

The official example: `custom_parent_class.rs` declares `#[qobject] #[qml_element] #[base = QQuickPaintedItem] #[qproperty(QColor, color)]`, overrides `unsafe fn paint(self: Pin<&mut Self>, painter: *mut QPainter)` with `#[cxx_override]`, inherits `size()` and `update()`, and calls `update()` from the color change signal; build.rs adds `.qt_module("Quick")` (https://github.com/KDAB/cxx-qt/blob/main/examples/qml_features/rust/src/custom_parent_class.rs, qml_features build.rs above). QML instantiates it like any item (https://github.com/KDAB/cxx-qt/blob/main/examples/qml_features/qml/pages/CustomParentClassPage.qml). Ferrous Systems' 2023 training does the same with a bare opaque `type QPainter;` (https://github.com/ferrous-systems/qt-training-2023/blob/main/crates/qt-gui-qquickpainteditem/src/image_painter.rs).

The GPU route: KDAB Labs' servo webview declares `#[base = "QQuickFramebufferObject"]` and overrides `createRenderer` to return `*mut QQuickFramebufferObjectRenderer`, plus `keyPressEvent`, `mouseMoveEvent`, `touchEvent` and `wheelEvent` taking raw event pointers (https://github.com/KDABLabs/cxx-qt-servo-webview/blob/main/src/webview.rs). The renderer is a non-QObject Rust type with `#[base = "QQuickFramebufferObject::Renderer"]`, overriding `render` and `synchronize` and inheriting `framebufferObject()` (https://github.com/KDABLabs/cxx-qt-servo-webview/blob/main/src/renderer.rs). Its one C++ header supplies what cxx cannot express: `using QQuickFramebufferObjectRenderer = QQuickFramebufferObject::Renderer;` for the nested class, a `constructUniquePtr<T>` factory, `blitFramebuffer` and `fboFromTexture` helpers, and QTouchEvent accessors (https://github.com/KDABLabs/cxx-qt-servo-webview/blob/main/cpp/helpers.h). The maintainer's summary in #1316: this is the route, "You will likely need some C++", "Generally it's all quite fiddly" (https://github.com/KDAB/cxx-qt/issues/1316). That repo pins cxx-qt 0.6 and was last pushed 2024-04-26, so its build.rs is stale but its bridge pattern still matches the 0.10 attributes above.

What cxx-qt-lib does not provide: QQuickItem, QQuickPaintedItem, QQuickFramebufferObject, QQuickWindow, QSGNode, QOpenGLFramebufferObject, or any `qt_quick` feature; the `qml` module holds QQmlEngine, QQmlApplicationEngine and QQmlImageProviderBase and the `quickcontrols` module holds QQuickStyle only (https://github.com/KDAB/cxx-qt/tree/main/crates/cxx-qt-lib/src). QSGNode bindings have been requested since 2023 with no movement (https://github.com/KDAB/cxx-qt/issues/604). No project pairing cxx-qt with libmpv or `mpv_render_context` turned up on GitHub code search.

Decision this enables: the video surface item can be a Rust type on either the QQuickPaintedItem or the QQuickFramebufferObject route, with a short C++ header beside it, or a plain C++ QQuickItem compiled through `cpp_file` and driven by the core through a `extern "C++Qt"` binding. Both are within the Cargo-only build. Which one, and whether libmpv's render API wants the FBO or the scene graph, is the mpv spike's question; nothing in cxx-qt forces the answer.

## 5. Known limits and open issues for this app's shape

### One long-lived core object

`#[qml_singleton]` on a `#[qml_element]` type makes "An instance of the `QObject` will be instantiated as a singleton in QML"; the generator emits `QML_SINGLETON`, so Qt's rule applies and the engine constructs and destroys it (https://kdab.github.io/cxx-qt/book/bridge/extern_rustqt.html, https://github.com/KDAB/cxx-qt/blob/main/crates/cxx-qt-gen/src/generator/cpp/qobject.rs, https://doc.qt.io/qt-6/qtqml-cppintegration-definetypes.html). The example is `singleton.rs` (https://github.com/KDAB/cxx-qt/blob/main/examples/qml_features/rust/src/singleton.rs). The engine builds the singleton on first use from QML, so the tokio runtime should start in `main` and the singleton's `Initialize` should find it, not create it. cxx-qt-lib's QQmlEngine binding exposes import paths, plugin paths, image providers and quit, and nothing for `rootContext`, `setContextProperty` or `setObjectOwnership` (https://github.com/KDAB/cxx-qt/blob/main/crates/cxx-qt-lib/src/qml/qqmlengine.rs); a QObject returned from an invokable without a parent becomes JavaScript-owned under Qt's default rule (https://doc.qt.io/qt-6/qtqml-cppintegration-data.html), so any model the core object hands out gets the core object as parent.

### The Rust struct inside the QObject

"The inner Rust struct of the QObject is owned by that QObject", dropped when the C++ object is destructed (https://kdab.github.io/cxx-qt/book/concepts/generated_qobject.html). `rust()` and `rust_mut()` are thin calls that return the boxed struct; there is no RefCell or runtime borrow check, only the static borrow of the `Pin<&mut Self>` (https://docs.rs/cxx-qt/latest/cxx_qt/trait.CxxQtType.html, https://github.com/KDAB/cxx-qt/blob/main/crates/cxx-qt/include/type.h). 0.7.0 removed the generated locking: "Qt/User C++ code is responsible for upholding Rusts Safety guarantees" (CHANGELOG 0.7.0). The reentrancy hazard follows: emitting a signal while an invokable still holds `Pin<&mut Self>` can run a QML handler synchronously that calls back into another invokable on the same object. No cxx-qt document classes this as UB or as a logic error; the maintainers describe C++ callers as "basically a giant unsafe block" (https://github.com/KDAB/cxx-qt/issues/427). The rule for the bridge object: finish every `rust_mut()` borrow before emitting, or emit through `queue`. The related use-after-free when a background thread touches the QObject while the GUI thread destroys it is by design; keep shared state in the core behind `Arc` and touch the QObject only through `CxxQtThread` (https://github.com/KDAB/cxx-qt/issues/1239).

Panics: cxx wraps every bridge function in `prevent_unwind`, whose comment reads "Goal is to make it impossible to propagate a panic across the C interface" and which aborts with "panic in ffi function ..., aborting." (https://github.com/dtolnay/cxx/blob/master/src/unwind.rs). A panic in `data()` or in a queued closure kills the shell. The bridge object catches or avoids panics and reports failures as events.

### List models behind the poster grid

`custom_base_class.rs` is the reference: `#[base = QAbstractListModel]` after `unsafe extern "C++Qt" { include!(<QtCore/QAbstractListModel>); #[qobject] type QAbstractListModel; }`; `#[qenum(CustomBaseClass)] enum Roles`; `#[qinvokable] #[cxx_override]` on `data(&self, &QModelIndex, i32) -> QVariant`, `rowCount` and `roleNames`, the last returning `QHash_i32_QByteArray`; `#[inherit] #[cxx_name = "beginInsertRows"] unsafe fn begin_insert_rows(self: Pin<&mut Self>, ...)` and the end, remove and reset counterparts, documented with "it is your responsibility to ensure end_insert_rows is called"; `#[inherit] #[qsignal] #[cxx_name = "dataChanged"]` for row updates (https://github.com/KDAB/cxx-qt/blob/main/examples/qml_features/rust/src/custom_base_class.rs). The maintainers declined to ship a safe list model: "This is now up to the downstream user", after suggesting a Drop guard for begin/end pairs and a future Vec-to-model crate that never appeared (https://github.com/KDAB/cxx-qt/issues/427). Rows updated from a background thread go through `queue` and then `dataChanged` on the Qt thread; the model type is Rust-defined, so `Threading` applies to it.

Posters: 0.9.0 added `QQmlEngine::add_image_provider(&QString, *mut QQmlImageProviderBase)`, but the provider base is an opaque `extern "C++Qt"` type and QQuickImageProvider is not bound (https://github.com/KDAB/cxx-qt/blob/main/crates/cxx-qt-lib/src/qml/qqmlengine.rs, .../qqmlimageproviderbase.rs). Serving posters as `file://` URLs from the core's image cache needs no provider at all and is the simpler route; a Rust image provider is possible in principle through `#[base = QQuickImageProvider]` and a `requestImage` override, but no source demonstrates it.

### Signals at volume

No source states a limit on `#[qsignal]` count per object; the generator emits one plain `Q_SIGNAL` declaration per signal (https://github.com/KDAB/cxx-qt/blob/main/crates/cxx-qt-gen/src/generator/cpp/signal.rs). Wrong-thread emission is prevented at compile time because the QObject is not Send; there is no runtime check (Threading page above). Const signals are still open for `extern "RustQt"` (https://github.com/KDAB/cxx-qt/issues/578). The costs that do exist are the per-queue allocation above and Qt's own signal dispatch; batching in the job is the answer for both.

### Pre-1.0 churn

"Stabilizing 1.0 API" has been open since 2023 and six issues still carry the 1.0 label (https://github.com/KDAB/cxx-qt/issues/555). Each minor release since 0.6 changed the bridge syntax or the build API; the servo demo and the Ferrous training both target 0.6 and would need rewriting for 0.10. Pin the exact version and budget a half day per cxx-qt minor. Other open items that could touch us: multiple inheritance is unsupported (https://github.com/KDAB/cxx-qt/issues/678); QFont and a few other types leak when passed by value to C++ (https://github.com/KDAB/cxx-qt/issues/1452); the qmllint export ignores QML files above Cargo.toml (build_systems page above).
