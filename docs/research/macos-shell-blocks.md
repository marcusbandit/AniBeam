# Building blocks for the macOS shell appendix

Research for ticket #8, written 2026-09-03 against primary sources. The reader is the person (and the Claude) who builds the macOS shell later from the spec's appendix: a SwiftUI app that owns the window, the input and the video surface, talks to the core through the uniffi bridge, and puts nothing with a rule in it. Vocabulary follows CONTEXT.md: core, shell, bridge, call, event, job, tick.

## Summary

The appendix can suggest these with confidence:

1. MPVKit 1.0.0 (July 2026) through Swift Package Manager, product `MPVKit` (LGPL), macOS 12 or later. It bundles mpv v0.41.0 and FFmpeg n8.1.2 as dynamic xcframeworks, and libmpv's public headers come with it.
2. Host the video surface in an `NSViewRepresentable` or `NSViewControllerRepresentable`. Two render paths have shipping code: libmpv's OpenGL render API in a `CAOpenGLLayer` (IINA), and a `CAMetalLayer` handed to mpv as `wid` with `vo=gpu-next`, `gpu-api=vulkan`, `gpu-context=moltenvk` (MPVKit's own demo).
3. uniffi 0.32.0: generate the Swift bindings in library mode with `uniffi-bindgen-swift`, ship the Rust core as an xcframework plus a Swift package, and deliver events through a foreign trait (`#[uniffi::export(foreign)]`) that a Swift class implements and forwards onto the main actor.
4. Sparkle 2.9.6 through Swift Package Manager, `SPUStandardUpdaterController` created in the `App` struct, `SUFeedURL` and `SUPublicEDKey` in Info.plist, EdDSA signed archives from `generate_appcast`.
5. A build that runs only on the builder's own Mac needs no Apple Developer Program membership and no notarisation: Xcode's automatic signing with a Personal Team, or Sign to Run Locally (ad hoc). Handing a build to another Mac needs Developer ID, the hardened runtime and notarisation, or the recipient walks through System Settings, Privacy and Security, Open Anyway on macOS 15 and later.
6. Media keys and Now Playing: `MPNowPlayingInfoCenter` plus `MPRemoteCommandCenter` from the MediaPlayer framework, available on macOS since 10.12.2; on macOS the shell must set `playbackState`, keep the handler targets alive, and leave mpv's own `input-media-keys` off.

The appendix should mark these uncertain:

7. The Metal path rests on an mpv patch that upstream closed unmerged (PR 7857) and that MPVKit carries itself; upstream's own `macvk` context opens its own window. The OpenGL path uses an API Apple deprecated but that IINA still ships.
8. The uniffi book does not say which thread a Swift trait implementation is called on; treat it as a Rust thread. Swift 6 strict concurrency support is partial (issue 2448 open).
9. An ad hoc signed app with the hardened runtime on may refuse to load embedded frameworks (Sparkle documents this for its own framework; MPVKit's frameworks are in the same position). I could not verify how Xcode's automatic signing handles this for a Personal Team.
10. Apple does not document how keyboard media keys reach `MPRemoteCommandCenter`, does not document which thread its handlers run on, and, per Apple's own DTS, does not document when Gatekeeper runs a full check.

## MPVKit: what it ships

MPVKit describes itself as "a toolkit for integrating mpv into iOS, macOS, tvOS applications, including build scripts for native libraries", forked from kingslay/FFmpegKit (https://raw.githubusercontent.com/mpvkit/MPVKit/main/README.md).

The latest release is `1.0.0`, published 2026-07-25, bundling mpv v0.41.0, FFmpeg n8.1.2, libplacebo v7.360.1 and MoltenVK v1.4.2; the notes say "Starting from this version, the version number will no longer follow mpv's version number" and "raise minimum OS versions to iOS 15.0 / macOS 12.0 / tvOS 15.0" (https://github.com/mpvkit/MPVKit/releases/tag/1.0.0). mpv v0.41.0 is also upstream's current stable, released 2025-12-21 (https://github.com/mpv-player/mpv/releases). Before 1.0.0 the project cut ten tagged builds between 2025-11-09 and 2026-06-25, several marked pre-release, so expect a release within weeks of an mpv or FFmpeg bump rather than a fixed cadence (https://github.com/mpvkit/MPVKit/releases).

`Package.swift` declares `platforms: [.macOS(.v12), .iOS(.v15), .tvOS(.v15), .visionOS(.v1)]` and two products, `MPVKit` and `MPVKit-GPL`. The source targets `_MPVKit` and `_FFmpeg` are stubs (`dummy.c`) whose only job is to pull in the binary targets and the system frameworks: `_MPVKit` depends on `Libmpv`, `_FFmpeg`, `Libuchardet`, `Libbluray` and, on macOS only, `Libluajit`, and links `AVFoundation` and `CoreAudio`; `_FFmpeg` links `AudioToolbox`, `CoreVideo`, `CoreFoundation`, `CoreMedia`, `Metal`, `VideoToolbox` and the libraries `bz2`, `iconv`, `expat`, `resolv`, `xml2`, `z`, `c++`. Every binary target is a `.binaryTarget(name:url:checksum:)` pointing at a release zip on GitHub, for example `https://github.com/mpvkit/openssl-build/releases/download/3.3.5/Libcrypto.xcframework.zip`; the pinned dependency versions are OpenSSL 3.3.5, GnuTLS 3.8.11, libass 0.17.5, libbluray 1.4.0, MoltenVK 1.4.2, libshaderc 2025.5.0, lcms2 2.17.0, libplacebo 7.360.1, libdav1d 1.5.3, libuchardet 0.0.8, LuaJIT 2.1.0-fix, and libsmbclient 4.15.13-2512 for the GPL variant only (https://raw.githubusercontent.com/mpvkit/MPVKit/main/Package.swift).

The 1.0.0 release attaches one `<Lib>.xcframework.zip` per library, in an LGPL and a `-GPL` flavour, plus `libmpv-all.zip` and `FFmpeg-all.zip` bundles (https://github.com/mpvkit/MPVKit/releases/tag/1.0.0). I downloaded `Libmpv.xcframework.zip` (19 MB): its macOS slice is `macos-arm64_x86_64/Libmpv.framework` with a `Versions/A/Libmpv` binary of 12.4 MB, `Headers/mpv/client.h`, `render.h`, `render_gl.h`, `stream_cb.h` and `Modules/module.modulemap`. The `Versions/A` layout is a dynamic framework, so the app embeds and signs it rather than linking it statically (https://github.com/mpvkit/MPVKit/releases/download/1.0.0/Libmpv.xcframework.zip).

The build script pins mpv `v0.41.0`, FFmpeg `n8.1.2`, libplacebo `7.360.1`, MoltenVK `1.4.2`, libass `0.17.5`, and configures mpv with `-Dlibmpv=true -Dgl=enabled -Dplain-gl=enabled -Dvulkan=enabled -Dmoltenvk=enabled`, adding `-Dcocoa=enabled -Dcoreaudio=enabled -Davfoundation=enabled -Dgl-cocoa=enabled -Dvideotoolbox-gl=enabled -Dlua=luajit` on macOS (https://raw.githubusercontent.com/mpvkit/MPVKit/main/Sources/BuildScripts/XCFrameworkBuild/main.swift).

Licence: "MPVKit source alone is licensed under the LGPL v3.0. MPVKit bundles (frameworks, xcframeworks), which include both libmpv and FFmpeg libraries, are also licensed under the LGPL v3.0. However, if the source code is built using the optional enable-gpl flag or prebuilt binaries with -GPL postfix are used, then MPVKit bundles become subject to the GPL v3.0." The GPL flavour adds Samba (smb://) support and nothing the shell needs (https://raw.githubusercontent.com/mpvkit/MPVKit/main/README.md).

## MPVKit: rendering, and what the Metal path rests on

libmpv's render API knows two backends: `MPV_RENDER_API_TYPE_OPENGL` ("opengl") and `MPV_RENDER_API_TYPE_SW` ("sw"). There is no Metal render API (https://raw.githubusercontent.com/mpv-player/mpv/master/include/mpv/render.h).

The mpv manual's `--wid` entry documents X11, win32 and Android and says nothing about macOS (https://github.com/mpv-player/mpv/blob/master/DOCS/man/options.rst, entry `--wid=<ID|-1>`). The only macOS Vulkan context upstream is `macvk`, described as "Vulkan on macOS with a metal surface through a translation layer (experimental)" (same file, entry `--gpu-context`). Its source, `video/out/vulkan/context_mac.m`, obtains its layer by creating mpv's own window through `MacCommon` (`p->vo_mac = [[MacCommon alloc] init:ctx->vo]`) and passes `p->vo_mac.layer` to `vkCreateMetalSurfaceEXT`; it does not read `--wid`, so it cannot draw into a view the shell owns (https://raw.githubusercontent.com/mpv-player/mpv/master/video/out/vulkan/context_mac.m). `vo=libmpv` is "For use with libmpv direct embedding. As a special case, on macOS it is used like a normal VO within mpv (cocoa-cb). Otherwise useless in any other contexts" (https://github.com/mpv-player/mpv/blob/master/DOCS/man/vo.rst).

MPVKit's README states: "Metal support only a patch version (#7857) and does not officially support it yet" (https://raw.githubusercontent.com/mpvkit/MPVKit/main/README.md). Upstream PR 7857, "video/out/vulkan: add MoltenVK context" by tmm1, was opened 2020-06-24 and closed 2023-11-20 without being merged (`state: CLOSED`, `mergedAt: null`) (https://github.com/mpv-player/mpv/pull/7857). MPVKit applies it as `Sources/BuildScripts/patch/libmpv/0001-player-add-moltenvk-context.patch`, alongside `0002-revert-build-static.patch` and `0003-enable-avfoundation-ao-tvos.patch` (https://github.com/mpvkit/MPVKit/tree/main/Sources/BuildScripts/patch/libmpv). The patch adds `video/out/vulkan/context_moltenvk.m`, registers a context with `.name = "moltenvk"`, reads the window id as a layer with `p->layer = (__bridge CAMetalLayer *)(intptr_t)ctx->vo->opts->WinID;` and creates the surface with `vkCreateMetalSurfaceEXT(inst, &info, NULL, &vk->surface)`; meson compiles it only on Darwin with both Vulkan and MoltenVK enabled (https://raw.githubusercontent.com/mpvkit/MPVKit/main/Sources/BuildScripts/patch/libmpv/0001-player-add-moltenvk-context.patch).

What this means for the appendix: on macOS a shell has three ways to put mpv's picture inside its own view. The OpenGL render API, which IINA ships (next section). The software render API, which is slow and which nobody in this research uses. And MPVKit's `moltenvk` context, which is fast and current but exists only because MPVKit keeps a closed upstream patch alive. Suggest the MPVKit Metal path, since it is what the package's own demo uses, and say that a future mpv bump could break it and that OpenGL is the fallback.

## MPVKit: hosting the render layer from SwiftUI

The macOS demo lives in `Demo/Demo-macOS/Demo-macOS/Player/`, with a `Metal/` and an `OpenGL/` folder (https://github.com/mpvkit/MPVKit/tree/main/Demo/Demo-macOS/Demo-macOS/Player). `ContentView.swift` uses only the Metal view (https://raw.githubusercontent.com/mpvkit/MPVKit/main/Demo/Demo-macOS/Demo-macOS/ContentView.swift).

The Metal path is three types:

- `struct MPVMetalPlayerView: NSViewControllerRepresentable`, whose `makeNSViewController` instantiates the controller and sets its delegate, and whose `Coordinator` is `@MainActor public final class Coordinator: MPVPlayerDelegate, ObservableObject` with `@Published` pause and HDR state (https://raw.githubusercontent.com/mpvkit/MPVKit/main/Demo/Demo-macOS/Demo-macOS/Player/Metal/MPVMetalPlayerView.swift).
- `final class MPVMetalViewController: NSViewController`, which sets `view.layer = metalLayer` and `view.wantsLayer = true`, creates mpv with `mpv_create()` and `mpv_initialize`, and sets, verbatim, `mpv_set_option(mpv, "wid", MPV_FORMAT_INT64, &metalLayer)`, `mpv_set_option_string(mpv, "vo", "gpu-next")`, `"gpu-api", "vulkan"`, `"gpu-context", "moltenvk"`, `"hwdec", "videotoolbox"`, `"input-media-keys", "yes"` (macOS only), plus `subs-match-os-language=yes`, `subs-fallback=yes`, `ytdl=no` and a `target-colorspace-hint` toggle. Events: `mpv_set_wakeup_callback` with `Unmanaged.passRetained(self).toOpaque()` as context, and a `readEvents()` that drains `mpv_wait_event` on `DispatchQueue(label: "mpv", qos: .userInitiated)`. Teardown: `mpv_set_wakeup_callback(mpv, nil, nil)` then `queue.sync { mpv_terminate_destroy(self.mpv) }`. HDR validation is disabled because of MoltenVK issue 2226 (https://raw.githubusercontent.com/mpvkit/MPVKit/main/Demo/Demo-macOS/Demo-macOS/Player/Metal/MPVMetalViewController.swift).
- `class MetalLayer: CAMetalLayer`, which overrides `drawableSize` to ignore the 1x1 size MoltenVK sets "to forcefully complete the presentation" (it flickers otherwise) and forces `wantsExtendedDynamicRangeContent` updates onto the main thread (https://raw.githubusercontent.com/mpvkit/MPVKit/main/Demo/Demo-macOS/Demo-macOS/Player/Metal/MetalLayer.swift).

The OpenGL path in the demo is `final class MPVOGLView: NSOpenGLView`: it creates the render context with `MPV_RENDER_API_TYPE_OPENGL` and a `get_proc_address` callback, registers `mpv_render_context_set_update_callback` and dispatches the redraw to the main thread, and its `draw()` calls `mpv_render_context_render` with `MPV_RENDER_PARAM_OPENGL_FBO` and `MPV_RENDER_PARAM_FLIP_Y` then `flushBuffer()`; events run on `DispatchQueue(label: "mpv", qos: .userInteractive)` (https://raw.githubusercontent.com/mpvkit/MPVKit/main/Demo/Demo-macOS/Demo-macOS/Player/OpenGL/MPVOGLView.swift).

The demo's entitlements enable the App Sandbox with `com.apple.security.files.user-selected.read-only`, `com.apple.security.network.client` and `com.apple.security.network.server`, and nothing that disables library validation (https://raw.githubusercontent.com/mpvkit/MPVKit/main/Demo/Demo-macOS/Demo-macOS/Demo_macOS.entitlements). So MPVKit's frameworks load fine under the sandbox.

Apple's side of the hosting: `NSViewRepresentable` and `NSViewControllerRepresentable` are available on macOS 10.15 and later, are `@MainActor`, and SwiftUI owns the wrapped view's `frame` and `bounds`, so the shell must not set them itself (https://developer.apple.com/documentation/swiftui/nsviewrepresentable, https://developer.apple.com/documentation/swiftui/nsviewcontrollerrepresentable).

Threading rules that both paths must respect, from libmpv itself: only one `mpv_render_*` function may run at a time per core; none of them may be called from inside the wakeup callback or the render update callback; with `MPV_RENDER_PARAM_ADVANCED_CONTROL` "it's a hard requirement" that `mpv_render_context_update` is called after each update callback, and breaking that promise "will freeze the mpv core thread forever" (https://raw.githubusercontent.com/mpv-player/mpv/master/include/mpv/render.h).

## IINA's libmpv layer as the reference for the OpenGL path

IINA's latest release is v1.4.4 (2026-06-24), after v1.4.3 (2026-05-20) and v1.4.2 (2026-04-16) (https://github.com/iina/iina/releases). The 1.4.0 notes say "Bumped mpv to 0.38.0", "Updated FFmpeg to 7.0.1" and "IINA 1.4.0 now requires macOS 10.15 Catalina for Intel Macs and macOS 12 Monterey for Apple Silicon Macs" (https://github.com/iina/iina/releases/tag/v1.4.0); no later 1.4.x note mentions another mpv bump, so I cannot say what 1.4.4 bundles. The develop branch sets `MACOSX_DEPLOYMENT_TARGET = 11` and `MACOSX_DEPLOYMENT_TARGET[arch=arm64] = 12` (https://github.com/iina/iina/blob/develop/Configs/Deployment.xcconfig).

IINA does not use MPVKit. `other/download_libs.sh` fetches prebuilt dylibs from `https://iina.io/dylibs/${ARCH}` (reading `filelist.txt`) into `deps/lib`, and the README says to build your own with the project's deps-buildscripts repository and add the `.dylib` files to the Frameworks group (https://raw.githubusercontent.com/iina/iina/develop/other/download_libs.sh, https://raw.githubusercontent.com/iina/iina/develop/README.md).

Render API. `MPVController.mpvInitRendering()` calls `mpv_render_context_create` with `MPV_RENDER_PARAM_API_TYPE` set to `MPV_RENDER_API_TYPE_OPENGL`, `MPV_RENDER_PARAM_OPENGL_INIT_PARAMS` carrying `get_proc_address`, and `MPV_RENDER_PARAM_ADVANCED_CONTROL` set to 1; the options it sets are `vo=libmpv`, `keepaspect=yes`, `gpu-hwdec-interop=auto`, and `hwdec` from the user preference (https://raw.githubusercontent.com/iina/iina/develop/iina/MPVController.swift, around lines 1450 to 1492). The hwdec preference maps `disabled` to `"no"`, `auto` to `"auto"`, `autoCopy` to `"auto-copy"`, default `auto` (https://raw.githubusercontent.com/iina/iina/develop/iina/Preference.swift). Nothing in these files mentions Metal.

View stack. `class VideoView: NSView` holds `lazy var videoLayer: ViewLayer`, sets `wantsLayer = true` and `wantsExtendedDynamicRangeOpenGLSurface = true`, and drives a `CVDisplayLink` whose callback calls `player.mpv.mpvReportSwap()` under a read lock; its comment says "locks must be used to coordinate uninitializing the view so that other threads do not attempt to use the mpv core while it is shutting down", and `uninit()` takes `lockAndSetOpenGLContext()` before `mpvUninitRendering()` (https://raw.githubusercontent.com/iina/iina/develop/iina/VideoView.swift). `class ViewLayer: CAOpenGLLayer` builds its pixel format with `kCGLPFAOpenGLProfile`, `kCGLPFAAccelerated`, `kCGLPFADoubleBuffer` and, for 10-bit, a 64-bit float colour size, creates the context with `CGLCreateContext` and enables `kCGLCEMPEngine`; `draw(inCGLContext:)` fills an `mpv_opengl_fbo` and calls `mpv_render_context_render` with `MPV_RENDER_PARAM_OPENGL_FBO`, `MPV_RENDER_PARAM_FLIP_Y` and `MPV_RENDER_PARAM_DEPTH`; `isAsynchronous` is true only during live resize; a recursive `displayLock` with a main-thread priority lock guards drawing (https://raw.githubusercontent.com/iina/iina/develop/iina/ViewLayer.swift).

The redraw loop. mpv's update callback is `mpvUpdateCallback`, which calls `layer.update()`; `update()` hops to `mpvGLQueue` and calls `display()`; `canDraw` returns `forceDraw || videoView.player.mpv.shouldRenderUpdateFrame()`, and `shouldRenderUpdateFrame()` is `mpv_render_context_update(mpvRenderContext)` masked with `MPV_RENDER_UPDATE_FRAME`. `lockAndSetOpenGLContext()` is `CGLLockContext` plus `CGLSetCurrentContext`, with a comment that the requirement "comes from mpv/render.h: the OpenGL context must be 'current' in the calling thread and must be the same context the mpv_render_context was created with". `mpvUninitRendering()` clears the update callback, calls `mpv_render_context_free`, then `mpv_destroy` (https://raw.githubusercontent.com/iina/iina/develop/iina/MPVController.swift, https://raw.githubusercontent.com/iina/iina/develop/iina/ViewLayer.swift).

Events. `mpv_set_wakeup_callback` points at `readEvents()`, which runs `mpv_wait_event(self.mpv, 0)` in a loop on a private `DispatchQueue(label: "com.colliderli.iina.controller", qos: .userInitiated)`, and `handleEvent` hops to `DispatchQueue.main.async` for anything that touches UI (https://raw.githubusercontent.com/iina/iina/develop/iina/MPVController.swift, around lines 1258, 1375, 1647).

The appendix can present this as the proven shape of an OpenGL host: an `NSView` with a `CAOpenGLLayer`, a display link that reports swaps, a dedicated queue for mpv events, and locks around teardown.

## uniffi: consuming the generated Swift package from Xcode

Version. The latest `uniffi` crate is 0.32.0, published 2026-06-30 (https://crates.io/api/v1/crates/uniffi); `v0.32.0` is the newest tag in the repository, which publishes no GitHub release objects (https://github.com/mozilla/uniffi-rs/tags). The changelog for 0.32.0 lists: "Traits can now be exported with `#[uniffi::export(foreign)]` for foreign-only implementations, or `#[uniffi::export(rust, foreign)]` for both Rust and foreign implementations" and "`#[uniffi::export(async_runtime = "tokio")]` can now be applied to trait exports" (https://raw.githubusercontent.com/mozilla/uniffi-rs/main/CHANGELOG.md).

What gets generated. Swift bindings are three files: "C header files declaring the FFI structs/functions used by the Rust scaffolding code", "A modulemap, which defines a Swift module for the C FFI definitions in the header file", and "A Swift source file that defines the Swift API used by consumers. This imports the FFI module". An interface becomes "a Swift `protocol TProtocol` and a concrete Swift `class T`", a record "a Swift `struct T` with public mutable fields", errors "Swift enums that conform to the `Error` protocol". The book's Swift overview does not state a minimum Swift or Xcode version (https://mozilla.github.io/uniffi-rs/latest/swift/overview.html).

Generating. The book's preferred tool is `uniffi-bindgen-swift`, a binary the project builds itself from `fn main() { uniffi::uniffi_bindgen_swift() }`; it "always inputs a library path and runs in 'library mode'", and its flags are `--swift-sources`, `--headers`, `--modulemap`, `--modulemap-filename`, `--module-name` and `--xcframework` ("Generate a Xcframework-compatible modulemap"). Example: `cargo run -p uniffi-bindgen-swift -- target/release/mylibrary.a build/swift/Modules --xcframework --modulemap --modulemap-filename mymodule.modulemap` (https://mozilla.github.io/uniffi-rs/latest/swift/uniffi-bindgen-swift.html). The `[bindings.swift]` keys in `uniffi.toml` are `cdylib_name`, `module_name`, `ffi_module_name`, `ffi_module_filename`, `generate_module_map`, `omit_argument_labels`, `generate_immutable_records`, `mutable_records`, `custom_types`, `rename`, `omit_localized_error_conformance`, `generate_case_iterable_conformance`, `generate_codable_conformance`, `omit_checksums` and `link_frameworks` (https://mozilla.github.io/uniffi-rs/latest/swift/configuration.html).

Packaging. The book's module page says "If you are creating an XCFramework with this code, make sure to rename the modulemap file to `module.modulemap`, the default value expected by Clang and XCFrameworks for exposing the C FFI library to Swift" and shows the manual `swiftc ... -Xcc -fmodule-map-file=exampleFFI.modulemap` compile (https://mozilla.github.io/uniffi-rs/latest/swift/module.html). The Xcode page covers only the in-project route: a build rule that runs `uniffi-bindgen generate $INPUT_FILE_PATH --language swift --out-dir $INPUT_FILE_DIR/Generated` on `.udl` files, a phase that builds the Rust crate to a static library and links it, `#include "exampleFFI.h"` in the bridging header, and the note that "You do _not_ need to add the generated Swift code to the list of 'Compile Sources'" (https://mozilla.github.io/uniffi-rs/latest/swift/xcode.html). The book does not describe building an xcframework or a Swift package.

Mozilla's own consumer pattern fills that gap. `rust-components-swift` is a Swift package whose `Package.swift` references the compiled Rust code as `.binaryTarget` xcframework zips (URL plus checksum, e.g. `MozillaRustComponents.xcframework.zip`) with the generated Swift sources as ordinary source targets that depend on a wrapper target, and apps add it as a normal package dependency by tag (https://raw.githubusercontent.com/mozilla/rust-components-swift/main/README.md, https://raw.githubusercontent.com/mozilla/rust-components-swift/main/Package.swift). The xcframework is built by `build-xcframework.sh` in application-services: `cargo build --lib --target <triple>` per target, `lipo -create` for the simulator slice, a hand-assembled `.framework` with a `Headers/` directory holding the generated header and module map, then `zip -9 -r`. That script covers iOS targets only and does not call `xcodebuild -create-xcframework` (https://raw.githubusercontent.com/mozilla/application-services/main/megazords/ios-rust/build-xcframework.sh).

Suggestion for the appendix, with the caveat that no first-party document shows the macOS variant end to end: build the core as a static library for `aarch64-apple-darwin` and `x86_64-apple-darwin`, `lipo` them, generate headers and an xcframework module map with `uniffi-bindgen-swift --xcframework`, wrap the slice in an xcframework, and ship a Swift package with one `binaryTarget` and one source target containing the generated `.swift` file. Xcode consumes that as a local package. Every claim in that sentence except the macOS triples and the `create-xcframework` step is sourced above; those two are standard Apple tooling I did not verify from a uniffi document.

Object rules the shell must know. "Uniffi enforces all interfaces are `Send + Sync`", "The Rust struct must not expose any methods that take `&mut self`", every object "on the heap using `Arc`", foreign handles hold an `Arc` reference and their destructors "will only drop their reference and may not drop the Rust object", and foreign code may call an object from several threads at once (https://mozilla.github.io/uniffi-rs/latest/types/interfaces.html). A call from the shell into the core is therefore a plain synchronous method on a Swift class; if the core blocks, the calling Swift thread blocks. The spec's rule that calls return fast is what keeps the main actor responsive; the bridge adds no protection.

## uniffi: how events reach the main actor

The mechanism is a foreign trait. "#[uniffi::export(rust, foreign)]" exports a trait both sides may implement, "#[uniffi::export(foreign)]" one only the shell implements; in UDL it is `[Trait, WithForeign]`. Parameters are passed by value ("References in foreign trait methods aren't supported"), methods must return `Result<>`, and an error type that does not implement `From<uniffi::UnexpectedUniFFICallbackError>` makes the generated code panic on an unexpected foreign error. The trait carries `Send + Sync`, and in Swift the implementation is "a class conforming to a protocol" that the shell instantiates and hands to a Rust function (https://mozilla.github.io/uniffi-rs/latest/foreign_traits.html). The older `callback interface` form is "soft deprecated, remain now for backwards compatibility"; it uses `Box<dyn T>` rather than `Arc`, and the book notes that foreign methods "should be safe to call from multiple threads at once, but Rust can not enforce this in the foreign code" (https://mozilla.github.io/uniffi-rs/latest/types/callback_interfaces.html).

So the shape for the spec is: the core exposes `subscribe(listener: Arc<dyn EventListener>)`, the shell passes a Swift object conforming to the generated `EventListener` protocol, and the core calls `listener.on_event(event)` for every event, with `Event` as a record or enum the bridge copies across by value.

Which thread. The book does not say which thread a foreign trait method runs on. The call is a synchronous C function pointer invocation from Rust, so it runs on whatever Rust thread makes it; with tokio inside the core that is a tokio worker, never the main thread. This is inference from the FFI design, not a quoted statement. The Swift implementation must therefore hop itself: `Task { @MainActor in ... }` or `DispatchQueue.main.async`, or hand the event to an `AsyncStream` continuation (thread safe by design) that a SwiftUI view consumes with `for await` on the main actor. The book offers no `AsyncStream` or Combine pattern; the appendix should present one as the shell's own convention.

Swift 6. The overview says most generated code conforms to `Sendable` but async code does not yet, tracked in issue 2448 (https://mozilla.github.io/uniffi-rs/latest/swift/overview.html), and that issue is still open: callbacks are the hard case because "user-implemented objects cannot be simply annotated as sendable" (https://github.com/mozilla/uniffi-rs/issues/2448). 0.31.2 fixed a "strict concurrency warning with callback interface tables" (https://raw.githubusercontent.com/mozilla/uniffi-rs/main/CHANGELOG.md). uniffi's own Swift test declares its trait implementation as `final class SwiftAsyncParser: AsyncParser, @unchecked Sendable` (https://raw.githubusercontent.com/mozilla/uniffi-rs/main/fixtures/futures/tests/bindings/test_futures.swift). Suggest the listener class be `final` and `@unchecked Sendable`, and that the generated target compile in Swift 5 language mode until 2448 closes.

Async, if the spec wants it. Rust `async fn`s exported with `#[uniffi::export]` become foreign native futures; "the foreign bindings supply the 'executor'", "There's no requirement for a Rust event loop", and "The async Rust code runs in a `Future::poll` method, inside the foreign event loop. This code never blocks" (https://mozilla.github.io/uniffi-rs/latest/futures.html, https://mozilla.github.io/uniffi-rs/latest/internals/async-overview.html). In Swift they are called as `await alwaysReady()`, `try await fallibleMe(doFail: false)` or `async let`, and a Swift-implemented async trait method is `func asString(delayMs: Int32, value: Int32) async -> String` (https://raw.githubusercontent.com/mozilla/uniffi-rs/main/fixtures/futures/tests/bindings/test_futures.swift). uniffi has no cancellation; the book says to "build your cancellation in a separate, library specific channel; for example, exposing a `cancel()` method" (https://mozilla.github.io/uniffi-rs/latest/futures.html). Given the settled design (tokio behind a synchronous facade, jobs report through events), the shell needs no async exports at all.

## Sparkle for updates

Version. 2.9.6 was published 2026-08-17, after 2.9.5 (2026-08-02), 2.9.4 (2026-07-03), 2.9.3 (2026-06-08) and 2.9.2 (2026-05-17) (https://github.com/sparkle-project/Sparkle/releases). 2.9.6 is a security release ("Harden safety of installer moving the download archive", "Reject package based installs when signing validation failed") (https://github.com/sparkle-project/Sparkle/releases/tag/2.9.6).

Requirements. The 2.9.6 README states "Runtime: macOS 10.13 or later" and "Build: Latest major Xcode (stable or beta, whichever is latest) and one major version less", and lists "Updates are verified using EdDSA signatures and Apple Code Signing" and "Supports Sandboxed applications in Sparkle 2" (https://raw.githubusercontent.com/sparkle-project/Sparkle/2.9.6/README.markdown). `Package.swift` at tag 2.9.6 declares `platforms: [.macOS(.v10_13)]`, product `Sparkle`, and a single `.binaryTarget` downloading `https://github.com/sparkle-project/Sparkle/releases/download/2.9.6/Sparkle-for-Swift-Package-Manager.zip` with a checksum (https://github.com/sparkle-project/Sparkle/blob/2.9.6/Package.swift). The head of the `2.x` branch already says `platforms: [.macOS(.v12)]` while still pointing at the 2.9.6 zip, so the next release line raises the floor to macOS 12 (https://github.com/sparkle-project/Sparkle/blob/2.x/Package.swift). The upgrading page's "Sparkle 2 now requires macOS 10.11" is stale against both (https://sparkle-project.org/documentation/upgrading/).

Integration. Add the package `https://github.com/sparkle-project/Sparkle` through File, Add Packages; CocoaPods is marked deprecated, Carthage uses `binary "https://sparkle-project.org/Carthage/Sparkle.json"`, and a manual drop-in of `Sparkle.framework` also works. In "Frameworks, Libraries, and Embedded Content" set Sparkle to Embed and Sign. Info.plist needs `SUFeedURL` and `SUPublicEDKey`, and "your app bundle must have an incrementing and properly formatted `CFBundleVersion` key" (https://sparkle-project.org/documentation/).

SwiftUI wiring, from the programmatic setup page: create `SPUStandardUpdaterController(startingUpdater: true, updaterDelegate: nil, userDriverDelegate: nil)` in the `App` struct's `init()`, and put a `CheckForUpdatesView(updater: updaterController.updater)` into `.commands { CommandGroup(after: .appInfo) { ... } }`; `CheckForUpdatesView` observes `SPUUpdater.canCheckForUpdates` through a small `CheckForUpdatesViewModel`. Passing `startingUpdater: false` defers the start to `startUpdater()` (https://sparkle-project.org/documentation/programmatic-setup/).

Keys and appcast. `./bin/generate_keys` runs once, stores the private key in the login Keychain and prints the public key for `SUPublicEDKey` (https://sparkle-project.org/documentation/). Put the `.app` in "a .dmg, .zip, .tar.*, or .aar"; "you must cryptographically sign your updates"; `generate_appcast` over the archive folder emits the appcast with the EdDSA signature and length and builds delta updates; `sparkle:version` is the machine version (e.g. "1248"), `sparkle:shortVersionString` the human one, and `sparkle:minimumSystemVersion` gates an item (https://sparkle-project.org/documentation/publishing/). Behaviour keys with defaults: `SUEnableAutomaticChecks` (unset means the user is asked on second launch), `SUScheduledCheckInterval` 86400 with a one hour minimum, `SUAutomaticallyUpdate` NO, `SUAllowsAutomaticUpdates`, `SUShowReleaseNotes` YES, `SUVerifyUpdateBeforeExtraction` NO, `SURequireSignedFeed` NO, `SUEnableInstallerLauncherService` NO (https://sparkle-project.org/documentation/customization/).

What Sparkle verifies, from its source. For bundle updates "we check both the EdDSA and Apple code signing signatures"; if EdDSA fails and signed archives are required, the fallback checks "if the archive is Developer ID signed with a team ID that matches the host"; a new bundle "must meet any one of: old and new Ed(DSA) public keys are the same and valid (it allows change of Code Signing identity), or old and new Code Signing identity are the same and valid"; "Sparkle only supports rotation, but not removal of (Ed)DSA keys", and "At least one method of signature verification must be valid" (https://raw.githubusercontent.com/sparkle-project/Sparkle/2.x/Sparkle/SUUpdateValidator.m). The EdDSA migration page states the rotation rule the same way: with Developer ID on both old and new update, "Sparkle uses the matching Apple code signature to trust the change in Sparkle public keys" (https://sparkle-project.org/documentation/eddsa-migration/).

Security and signing advice from the docs, verbatim: "Serve updates over HTTPS and comply with Apple's App Transport Security requirements", "Notarize and code sign the application via Apple's Developer ID program (if possible)", "Sign the published update archive (dmg, zip, etc), binary delta updates, and installer packages with Sparkle's EdDSA (ed25519) signature". For distribution: "We recommend building your distributable app in Xcode by creating a `Product › Archive` and `Distribute App` choosing `Developer ID` method of distribution. Using Xcode's Archive Organizer will ensure Sparkle's helper tools are code signed properly for distribution" (https://raw.githubusercontent.com/sparkle-project/sparkle-project.github.io/master/documentation/index.md).

The paragraph that matters for a locally built app, verbatim: "If you enable Library Validation, which is part of the Hardened Runtime and required for notarization, you will also need to either sign your application with an `Apple Development` certificate for development (requires being in Apple's developer program), or disable library validation for Debug configurations only. Otherwise, the system may not let your application load Sparkle if you attempt to sign to run locally via an ad-hoc signature. This is not an issue for distribution when you sign your application with a Developer ID certificate" (same URL). The same constraint applies to MPVKit's frameworks and to the core's xcframework.

Sandboxing. Sparkle 2 supports sandboxed apps; a sandboxed app must set `SUEnableInstallerLauncherService` to `YES` (and `SUEnableDownloaderService` to `YES` if it has no network entitlement), keep `Installer.xpc` (and optionally `Downloader.xpc`), and add the entitlement `com.apple.security.temporary-exception.mach-lookup.global-name` with `$(PRODUCT_BUNDLE_IDENTIFIER)-spks` and `$(PRODUCT_BUNDLE_IDENTIFIER)-spki`; a non-sandboxed app needs none of that. Xcode re-signs the framework on embed but "will not re-sign the XPC Services and other helpers inside the framework", which is why the docs push Archive and Export for distribution builds (https://sparkle-project.org/documentation/sandboxing/).

What Sparkle cannot do for the first audience: an update feed only makes sense once builds are Developer ID signed and hosted over HTTPS. For a friend building on his own Mac, Sparkle is a later addition, and the appendix should say so.

## Code signing and notarisation

Running on the builder's own Mac. On Apple silicon, per Apple DTS: "On Apple silicon all code must be signed. If you don't intend to distribute the code, it's fine to use ad hoc signing (this is what you get in Xcode when you select the Sign to Run Locally option)" (https://developer.apple.com/forums/thread/698167). "Sign to Run Locally is Xcode's name for _ad hoc signing_ [1] which leaves your code without a stable designated requirement", and "[1] This is different from iOS's Ad Hoc distribution"; DTS recommends Apple Development signing for day-to-day work because a stable designated requirement matters for privacy prompts (https://developer.apple.com/forums/thread/723669). A free Apple account can sign in to Xcode as a Personal Team for on-device testing; the paid Apple Developer Program adds "Mac software notarization" and "Certificates, Identifiers & Profiles" (https://developer.apple.com/support/compare-memberships/). The program costs 99 USD per year and includes distributing "your Mac apps outside the Mac App Store using your Developer ID certificate and Apple's notarization process" (https://developer.apple.com/programs/). Notarisation is not needed to run what you build yourself: Apple's DTS observed that an ad hoc signed binary copied to another Mac over "sneaker net" ran without a Gatekeeper dialog, and that "If, for example, you uploaded this program to a web server and downloaded it using Safari, Safari would quarantine the download and the program would be rejected by Gatekeeper"; also "The exact circumstances under which Gatekeeper runs a full check of a program, and thus would generate this alert, are not documented. They also change regularly" (https://developer.apple.com/forums/thread/740680). These three are forum answers by Apple's Developer Technical Support, not reference documentation; I found no reference page that defines Sign to Run Locally.

The embedded frameworks problem. The hardened runtime enables library validation, which "prevents a program from loading frameworks, plug-ins, or libraries unless they're either signed by Apple or signed with the same Team ID as the main executable"; disabling it with `com.apple.security.cs.disable-library-validation` makes Gatekeeper run "extra security checks" (https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.disable-library-validation). DTS: "If library validation is enabled on an executable, the trusted execution system only allows the process to load code signed by Apple or with the same Team ID as the executable" and "Leave library validation enabled. Only disable it if your app needs to load plug-ins from other third-party developers" (https://developer.apple.com/forums/thread/706437). Entitlements go on executables only; "Shared libraries, frameworks, and in-process plug-ins inherit the entitlements of their host executable" (https://developer.apple.com/documentation/security/hardened-runtime). Sparkle's documentation says plainly that an ad hoc signed app with the hardened runtime on "may not" load its framework and offers two outs: sign with an Apple Development certificate, or disable library validation in Debug only (https://raw.githubusercontent.com/sparkle-project/sparkle-project.github.io/master/documentation/index.md). The appendix should say: for local builds, leave the Hardened Runtime capability off, or sign with a Personal Team development certificate; turn it on with Developer ID when notarising. I did not verify how Xcode's automatic signing treats MPVKit's binary targets under a Personal Team; that is the first thing to test on the builder's Mac.

Handing a build to another Mac. Gatekeeper "verifies that the software is from an identified developer, is notarized by Apple to be free of known malicious content, and hasn't been altered", and "requests user approval before opening downloaded software for the first time"; users can override unless a device management service forbids it (https://support.apple.com/guide/security/gatekeeper-and-runtime-protection-sec5599b66df/web). Since macOS Sequoia "users will no longer be able to Control-click to override Gatekeeper when opening software that isn't signed correctly or notarized. They'll need to visit System Settings > Privacy & Security to review security information for software before allowing it to run" (https://developer.apple.com/news/?id=saqachfa). Apple's user-facing steps: open System Settings, go to Privacy and Security, click Open Anyway, then Open again in the repeated warning; the exception is remembered (https://support.apple.com/en-us/102445). Beginning macOS 10.15 "All software built after June 1, 2019, distributed with Developer ID" must be notarised (https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution). Removing the quarantine attribute with `xattr` is something I could not source to an Apple page; it belongs in the appendix only as a "what the friend does on his own machine" note, if at all.

What notarisation needs. "Notarization of macOS software is not App Review. The Apple notary service is an automated system that scans your software for malicious content, checks for code-signing issues, and returns the results to you quickly." Requirements: all executables signed, a "Developer ID" certificate (not "Mac Distribution, ad hoc, Apple Developer, or local development certificates"), the Hardened Runtime enabled, a secure timestamp, no `com.apple.security.get-task-allow` set to true, the 10.9 or later SDK, and well-formed entitlements (https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution). "To upload a macOS app to be notarized, you must enable the Hardened Runtime capability" (https://developer.apple.com/documentation/security/hardened-runtime). The Xcode route is Product, Archive, then Distribute App and "Direct Distribution: Default settings to distribute a macOS app directly. Use this option to notarize a Developer ID app for direct distribution"; the custom flow also offers "Developer ID" and "Copy App: Distribute a macOS app without code signing" (https://developer.apple.com/documentation/xcode/distributing-your-app-for-beta-testing-and-releases). The command line route: `xcrun notarytool store-credentials "notarytool-password" --apple-id "<AppleID>" --team-id <DeveloperTeamID> --password <secret_2FA_password>` once (an app-specific password), then `xcrun notarytool submit <file> --keychain-profile "notarytool-password" --wait`, then `xcrun stapler staple "<App>.app"`; zip, UDIF disk image and flat installer package are accepted, a zip cannot be stapled so staple the app inside and re-zip; most submissions finish in five minutes (https://developer.apple.com/documentation/security/customizing-the-notarization-workflow). Manual signing is `codesign -s "Developer ID Application" -f --timestamp -o runtime --entitlements <file> <App>.app`, signed inside out (frameworks first), never with `--deep` (https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac). Package with `ditto -c -k --keepParent <dir> <zip>` or `hdiutil create -srcFolder ... -o <dmg>` plus `codesign` on the image; notarise only the outermost container; an app launched from inside a zip or dmg location gets translocated on first launch, so test a second launch too (https://developer.apple.com/documentation/xcode/packaging-mac-software-for-distribution).

App Sandbox. "To distribute a macOS app through the Mac App Store, you must enable the App Sandbox capability"; outside the store it is optional. A sandboxed player can only reach files through entitlements such as user-selected read-only access and the mechanisms Apple describes under "Accessing files from the macOS App Sandbox" (https://developer.apple.com/documentation/security/app-sandbox). Since the core scans whole library folders, the appendix should recommend no sandbox for the first version; MPVKit's demo shows the sandbox is possible if wanted later.

Personal Team expiry. Apple's membership page says Personal Team App IDs and registered devices "expire after 7 days" and provisioning profiles "will expire 7 days from issuance" (https://developer.apple.com/support/compare-memberships/). Whether a Mac app without restricted entitlements needs a profile at all, and so whether a Personal Team build keeps running past a week, I could not verify from an Apple page. Mark it uncertain and let the builder observe it.

## Media keys and Now Playing

Availability. `MPNowPlayingInfoCenter`, `MPRemoteCommandCenter`, `MPRemoteCommand`, `MPMediaItemArtwork.init(boundsSize:requestHandler:)`, `MPNowPlayingInfoPropertyElapsedPlaybackTime`, `MPNowPlayingInfoPropertyMediaType`, `MPRemoteCommandHandlerStatus` and `MPChangePlaybackPositionCommandEvent.positionTime` are all "macOS 10.12.2+" (https://developer.apple.com/documentation/mediaplayer/mpnowplayinginfocenter, https://developer.apple.com/documentation/mediaplayer/mpremotecommandcenter, https://developer.apple.com/documentation/mediaplayer/mpremotecommand, https://developer.apple.com/documentation/mediaplayer/mpmediaitemartwork/init(boundssize:requesthandler:), https://developer.apple.com/documentation/mediaplayer/mpnowplayinginfopropertyelapsedplaybacktime, https://developer.apple.com/documentation/mediaplayer/mpnowplayinginfopropertymediatype, https://developer.apple.com/documentation/mediaplayer/mpremotecommandhandlerstatus, https://developer.apple.com/documentation/mediaplayer/mpchangeplaybackpositioncommandevent/positiontime). `MPNowPlayingSession` is iOS 16, iPadOS 16, Mac Catalyst 16, tvOS 14 and visionOS 1 only; it is not available on macOS (https://developer.apple.com/documentation/mediaplayer/mpnowplayingsession).

The macOS rule. `MPNowPlayingInfoCenter` groups `playbackState` under "Setting the playback state in macOS" (https://developer.apple.com/documentation/mediaplayer/mpnowplayinginfocenter), and its discussion reads: "This property only applies to macOS. You must set this property every time the app begins or halts playback, otherwise remote control functionality may not work as expected" (https://developer.apple.com/documentation/mediaplayer/mpnowplayinginfocenter/playbackstate). The states are `unknown`, `playing`, `paused`, `stopped`, `interrupted` (https://developer.apple.com/documentation/mediaplayer/mpnowplayingplaybackstate). IINA does exactly this: `center.playbackState = paused ? .paused : .playing`, and `.stopped` when a session ends (https://raw.githubusercontent.com/iina/iina/develop/iina/NowPlayingInfoManager.swift).

The dictionary. Apple: "You set the values in the `nowPlayingInfo` dictionary and the system or the connected accessory handles displaying the information", and "provide values for as many information properties as you can" (https://developer.apple.com/documentation/mediaplayer/mpnowplayinginfocenter). IINA sets `MPMediaItemPropertyTitle`, `MPMediaItemPropertyAlbumTitle`, `MPMediaItemPropertyArtist`, `MPMediaItemPropertyPlaybackDuration`, `MPMediaItemPropertyArtwork`, `MPNowPlayingInfoPropertyMediaType`, `MPNowPlayingInfoPropertyAssetURL`, `MPNowPlayingInfoPropertyPlaybackQueueCount`, `MPNowPlayingInfoPropertyPlaybackQueueIndex`, `MPNowPlayingInfoPropertyChapterCount`, `MPNowPlayingInfoPropertyChapterNumber`, `MPNowPlayingInfoPropertyElapsedPlaybackTime`, `MPNowPlayingInfoPropertyPlaybackRate` and `MPNowPlayingInfoPropertyDefaultPlaybackRate`, and assigns the whole dictionary with `center.nowPlayingInfo = info` (https://raw.githubusercontent.com/iina/iina/develop/iina/NowPlayingInfoManager.swift). For AniBeam: title is the episode, artist the series, media type `MPNowPlayingInfoMediaType.video` (the value is an `NSNumber` wrapping `none`, `audio` or `video`, https://developer.apple.com/documentation/mediaplayer/mpnowplayinginfopropertymediatype).

Elapsed time. "Elapsed time is automatically calculated, by the system, from the previously provided elapsed time and the playback rate. It isn't necessary to update this property frequently" (https://developer.apple.com/documentation/mediaplayer/mpnowplayinginfopropertyelapsedplaybacktime). So the shell writes elapsed time and rate when playback starts, pauses, seeks or changes speed, not on every tick; ticks still flow to the core for the view and mark rules.

Artwork. `init(boundsSize: CGSize, requestHandler: @escaping (CGSize) -> NSImage)` on macOS; "The request handler returns the image in the newly requested size. The requested size must be less than the `boundsSize` parameter" (https://developer.apple.com/documentation/mediaplayer/mpmediaitemartwork/init(boundssize:requesthandler:)). Apple does not say whether the handler runs on a background thread or how often; IINA's handler crops the poster to the aspect ratio and resizes it inside the closure (https://raw.githubusercontent.com/iina/iina/develop/iina/NowPlayingInfoManager.swift). Keep the closure pure and cheap.

Commands. Use `MPRemoteCommandCenter.shared()`; "Don't create instances of this class yourself" (https://developer.apple.com/documentation/mediaplayer/mpremotecommandcenter). "When an accessory or iOS user interface generates a remote control event, the system notifies the corresponding command object on the shared MPRemoteCommandCenter instance. That command object executes any attached handlers" (https://developer.apple.com/documentation/mediaplayer/mpremotecommand). `addTarget(handler: @escaping (MPRemoteCommandEvent) -> MPRemoteCommandHandlerStatus) -> Any` returns "An opaque object associated with the designated handler. You must retain this object or pass it to the `removeTarget(_:)` method to remove the handler" (https://developer.apple.com/documentation/mediaplayer/mpremotecommand/addtarget(handler:)). Handler results are `success`, `noSuchContent`, `noActionableNowPlayingItem`, `deviceNotFound`, `commandFailed` (https://developer.apple.com/documentation/mediaplayer/mpremotecommandhandlerstatus). `MPSkipIntervalCommand.preferredIntervals` is an array of seconds (https://developer.apple.com/documentation/mediaplayer/mpskipintervalcommand/preferredintervals) and `MPChangePlaybackPositionCommandEvent.positionTime` is the target position in seconds (https://developer.apple.com/documentation/mediaplayer/mpchangeplaybackpositioncommandevent/positiontime). Apple does not document which thread handlers run on; hop to the main actor before touching state.

The set a video player registers, from IINA's `RemoteCommandController` in `AppDelegate.swift`: `playCommand`, `pauseCommand`, `togglePlayPauseCommand`, `stopCommand`, `nextTrackCommand`, `previousTrackCommand`, `skipForwardCommand`, `skipBackwardCommand`, `changeRepeatModeCommand`, `changePlaybackRateCommand`, `changePlaybackPositionCommand`, each `addTarget { event in ... }` returning `.success`, with skip intervals read from the seek key bindings and defaulting to 15 seconds; the whole thing is gated on `static var useSystemMediaControl: Bool = Preference.bool(for: .useMediaKeys)`, and the comment says "IINA is assuming control over a shared macOS feature it is critical that IINA releases control when no media is open" (https://raw.githubusercontent.com/iina/iina/develop/iina/AppDelegate.swift). For AniBeam, next and previous track map to next and previous episode, which is a call into the core.

Media keys. Apple's MediaPlayer pages never mention keyboards, the Touch Bar or which app receives the keys; the statement that F7 to F9 route through `MPRemoteCommandCenter` is not in the reference documentation. What is verifiable: both IINA (above, "macOS media keys and remote commands") and mpv itself treat `MPRemoteCommandCenter` as the media key path. mpv's macOS build has `osdep/mac/remote_command_center.swift`, `class RemoteCommandCenter: EventSubscriber`, which registers `playCommand`, `pauseCommand`, `stopCommand`, `togglePlayPauseCommand`, `nextTrackCommand`, `previousTrackCommand`, `seekForwardCommand`, `seekBackwardCommand` and `changePlaybackPositionCommand`, and writes `infoCenter.playbackState` and the now playing dictionary (https://raw.githubusercontent.com/mpv-player/mpv/master/osdep/mac/remote_command_center.swift); it is created in `app_hub.swift` under `#if HAVE_MACOS_MEDIA_PLAYER` and started by `startRemote()` (https://raw.githubusercontent.com/mpv-player/mpv/master/osdep/mac/app_hub.swift). The manual's `--input-media-keys` says "Default: yes (except for libmpv). macOS and Windows only" (https://github.com/mpv-player/mpv/blob/master/DOCS/man/options.rst, entry `--input-media-keys`). MPVKit's demo sets `input-media-keys=yes`, which hands the keys and the Now Playing widget to mpv's own handler (https://raw.githubusercontent.com/mpvkit/MPVKit/main/Demo/Demo-macOS/Demo-macOS/Player/Metal/MPVMetalViewController.swift). The shell must not do that: leave the option at libmpv's default of no, and own `MPRemoteCommandCenter` and `MPNowPlayingInfoCenter` itself, so ticks, views and marks keep flowing through the core. I did not trace which line of mpv's code ties the option value to `startRemote()`; the default is enough for the appendix.

Apple's "Becoming a now playable app" is a sample code page tied to WWDC19 session 501 with no article body on the web, only pointers to `NowPlayable.swift` and `NowPlayableBehavior` in the download (https://developer.apple.com/documentation/mediaplayer/becoming-a-now-playable-app). I could not quote guidance from it.
