# uniffi constraints on the core API and Swift event delivery

Research ticket #5, part of the native line map #2. Checked on 2026-09-03 against the uniffi-rs book, the uniffi-rs repository at `main` and tag `v0.32.0`, crates.io, docs.rs, swift.org, and a smoke test run on this Linux host. Vocabulary follows `CONTEXT.md`: core, shell, bridge, call, event, job.

## Summary

1. Pin uniffi 0.32.0 (2026-06-30, git tag only, no newer pre-release) and describe the API with proc-macros and `uniffi::setup_scaffolding!()`; no UDL, no `build.rs`.
2. Generate the Swift bindings on Linux from the Linux `.so` with `uniffi-bindgen-swift`; the embedded metadata is platform neutral. Hand over `core.swift`, `coreFFI.h`, `module.modulemap`, `uniffi.toml`, the commit and the uniffi version; the Mac builds the `staticlib` per Apple target and the xcframework, which only Xcode can do.
3. The Linux Swift toolchain compiles and runs the generated package: proven here with `swift:6.3` (Swift 6.3.3) against the Linux `.so`, which is also what uniffi's own CI does in `swift:6.3-noble`.
4. `Call` and `Event` can be `#[derive(uniffi::Enum)]` enums with named-field variants over records, `Option`, `Vec`, `HashMap`, `SystemTime`, `Duration`, `Vec<u8>` and error enums; Swift sees enums with labelled associated values that are `Sendable`, `Equatable` and `Hashable`.
5. Out of the enums: `usize`, `u128`, `char`, tuples, arrays, generics, tuple structs, struct errors, references, and `PathBuf` or `Url` without a custom type; the probe reproduced each refusal on 0.32.0.
6. Async calls become `async throws` in Swift and are polled by Swift's executor; tokio stays inside the core behind `Runtime::spawn`; a cancelled Swift `Task` never reaches Rust, so every job carries a cancel call.
7. Events reach the macOS shell through a foreign trait, `#[uniffi::export(foreign)] EventListener`, stored once by `subscribe`; the core invokes it directly on the tokio thread that emits, and the Swift listener hops to the main actor itself.
8. The core is one `#[derive(uniffi::Object)]` type behind `Arc`, `Send + Sync`, `&self` only, state under std locks; Swift gets `open class Core: @unchecked Sendable` with a refcount lifetime, callable from any thread.
9. Swift 6 strict concurrency is partial: listener classes must be `Sendable`, Xcode 26's default main-actor isolation must stay off for the generated module, and async foreign traits have open issues; compile the generated file in Swift 5 language mode as uniffi's CI does.
10. One definition serves both bridges because uniffi's derives are attributes on the core's own types; the last section lists the rules, and ticket #3 supplies the cxx-qt half for #15.

## Current release, proc-macros versus UDL, Swift bindings from a Linux host

### Current release

The current `uniffi` crate is 0.32.0, published 2026-06-30. There is no newer pre-release; crates.io reports `max_version 0.32.0`, `max_stable_version 0.32.0`. Source: https://crates.io/api/v1/crates/uniffi and https://crates.io/crates/uniffi. The project publishes git tags only, never GitHub releases (the releases page is empty); tag `v0.32.0` was cut 2026-06-30. Source: https://github.com/mozilla/uniffi-rs/tags and https://github.com/mozilla/uniffi-rs/releases.

Changelog entries that shape this work, all from https://github.com/mozilla/uniffi-rs/blob/main/CHANGELOG.md:

- 0.32.0 deprecates `#[uniffi::export(with_foreign)]` in favour of `#[uniffi::export(foreign)]` (foreign implementations only) or `#[uniffi::export(rust, foreign)]` (both sides). It adds recursive enums (`indirect` in Swift), `Box<T>` in enum variants and arguments, `#[uniffi::export(async_runtime = "tokio")]` on trait exports, the `mutable_records` option, zero-copy `&[u8]` arguments (Swift `Data`, synchronous functions only), and it changes `--config` to expect a global config file.
- 0.31.2 fixes a Swift strict-concurrency warning in the callback interface tables and a BOM bug in `FfiConverterString`.
- 0.31.1 fixes a memory leak in the Swift async code path.
- 0.31.0 removes `--lib-file`, deprecates `--library` (the source path is auto-detected as a library or a UDL file), and changes method checksums so that bindings generated with one uniffi version refuse to load a library built with another. MSRV 1.87 at that release; CI runs 1.90 now.
- 0.30.0 moves object handles to `u64` and requires `#[uniffi::trait_interface]` on UDL trait interfaces.
- Unreleased on `main`: `uniffi-bindgen ... src:<crate>` parses Rust sources without building the library, `#[uniffi::export(remote)]` for traits from other crates (no foreign implementations), and `&mut [u8]` arguments (Swift `inout Data`).

The practical rule from the 0.31.0 entry: the Mac side must build the core from the same commit and the same pinned uniffi version as the generated Swift, or the library refuses to initialise.

### Proc-macros versus UDL

The book presents both routes as equals and never states a recommendation. Landing page: "UniFFI requires you to describe your interface via either proc-macros or in an Interface Definition Language (based on WebIDL) file." Source: https://mozilla.github.io/uniffi-rs/latest/. With proc-macros the crate needs no `build.rs`: "If you are only using proc macros, you can skip `build.rs` entirely! All you need to do is add this to the top of `lib.rs` `uniffi::setup_scaffolding!();`". The namespace defaults to the crate name. Source: https://mozilla.github.io/uniffi-rs/latest/tutorial/Rust_scaffolding.html.

The proc-macro chapter gives the reason to prefer it: it avoids "the need to duplicate them in a UDL file and so avoiding the possibility for the two to get out of sync". Mixing is allowed with separate `impl` blocks, and the crate name must then match the UDL namespace. Bindings for a proc-macro crate must be generated from the built library (or the unreleased `src:` mode), never from a UDL path. `#[cfg()]` does not work inside `#[uniffi::export]` blocks; put it before the attribute. Source: https://mozilla.github.io/uniffi-rs/latest/proc_macro/index.html. The bindings tutorial adds the strongest directional statement: "Generating from a single UDL is deprecated". Source: https://mozilla.github.io/uniffi-rs/latest/tutorial/foreign_language_bindings.html. Callback interfaces are "(soft) deprecated" in favour of foreign traits, which exist in the macro form only as `#[uniffi::export(foreign)]`. Source: https://mozilla.github.io/uniffi-rs/latest/types/callback_interfaces.html and https://mozilla.github.io/uniffi-rs/latest/proc_macro/traits.html.

Decision this enables: the core uses proc-macros only, `uniffi::setup_scaffolding!()` at the crate root, no UDL, no `build.rs`.

### Generating Swift bindings on a Linux host

The book's bindgen setup is a project bin: `[[bin]] name = "uniffi-bindgen"` whose `main` calls `uniffi::uniffi_bindgen_main()`, built with the `cli` feature, then `cargo build --release` and `cargo run --bin uniffi-bindgen generate target/release/libcore.so --language swift --out-dir out`. It must run inside the cargo workspace. Source: https://mozilla.github.io/uniffi-rs/latest/tutorial/foreign_language_bindings.html. The CLI source confirms `--library` is a deprecated no-op and `--out-dir` is required. Source: https://github.com/mozilla/uniffi-rs/blob/main/uniffi/src/cli/uniffi_bindgen.rs. After writing the Swift file the generator tries `swift-format` and prints a warning when none exists (observed on this host); `--no-format` silences it. Source: https://github.com/mozilla/uniffi-rs/blob/main/uniffi_bindgen/src/bindings/swift/mod.rs.

A second bin, `uniffi-bindgen-swift` (`main` calls `uniffi::uniffi_bindgen_swift()`), gives finer control: it always runs in library mode, and it selects which files to emit with `--swift-sources`, `--headers`, `--modulemap`, plus `--xcframework`, `--module-name` and `--modulemap-filename`. Source: https://mozilla.github.io/uniffi-rs/latest/swift/uniffi-bindgen-swift.html and https://github.com/mozilla/uniffi-rs/blob/main/uniffi/src/cli/swift.rs.

Generating on Linux from the Linux `.so` is supported by design: "UniFFI metadata embedded in libraries is platform and architecture agnostic, which might be useful in cross-compiled environments. You must still take care here, as the underlying Rust code could have its own conditional compilation". Source: https://mozilla.github.io/uniffi-rs/latest/tutorial/foreign_language_bindings.html (section "Cross platform and multi architecture support"). The metadata extractor parses ELF, PE, Mach-O (including fat), archives and COFF alike. Source: https://github.com/mozilla/uniffi-rs/blob/main/uniffi_bindgen/src/macro_metadata/extract.rs. The one caveat is real for us: an export behind `#[cfg(target_os = "macos")]` would be missing from Swift generated off the Linux build, so the exported surface must carry no platform cfg gates.

### Generated files and the Swift package layout

For a component named `core`, generation produces `core.swift`, `coreFFI.h` and `coreFFI.modulemap`; the module name defaults to the namespace, the FFI module to `{module_name}FFI`. Source: https://mozilla.github.io/uniffi-rs/latest/swift/overview.html and https://github.com/mozilla/uniffi-rs/blob/main/uniffi_bindgen/src/bindings/swift/gen_swift/mod.rs. The module map template emits `module X { header ...; export *; use "Darwin"; ... }`, and `--xcframework` changes exactly one word, `module` becomes `framework module`. Source: https://github.com/mozilla/uniffi-rs/blob/main/uniffi_bindgen/src/bindings/swift/templates/ModuleMapTemplate.modulemap.

The book's compile recipe is a single `swiftc` call with `-Xcc -fmodule-map-file=coreFFI.modulemap`, `-L` and `-l` for the Rust library, and the note "If you are creating an XCFramework with this code, make sure to rename the modulemap file to `module.modulemap`". Source: https://mozilla.github.io/uniffi-rs/latest/swift/module.html. The Xcode chapter is written around build phases and points to `examples/app/ios/xc-universal-binary.sh`, which runs `cargo rustc --lib --crate-type staticlib --target <apple target>` per architecture. Source: https://mozilla.github.io/uniffi-rs/latest/swift/xcode.html and https://github.com/mozilla/uniffi-rs/blob/main/examples/app/ios/xc-universal-binary.sh. The book has no SwiftPM or XCFramework assembly walkthrough; the README points at third-party `cargo swift` and `uniffi-starter` for that. Source: https://github.com/mozilla/uniffi-rs/blob/main/README.md. The `xcodebuild -create-xcframework -library ... -headers ...` step comes from Apple's documentation, which is outside the ticket's source set: https://developer.apple.com/documentation/xcode/creating-a-multi-platform-binary-framework-bundle.

Split of work this enables:

- On Linux, the core's owner runs `cargo build --release`, then `uniffi-bindgen-swift target/release/libcore.so Sources --swift-sources`, `... Headers --headers`, and `... Headers --modulemap --xcframework --modulemap-filename module.modulemap --module-name coreFFI`, and hands over `Sources/core.swift`, `Headers/coreFFI.h`, `Headers/module.modulemap`, the `uniffi.toml`, the git commit and the pinned uniffi version. This exact sequence ran on this host (see the smoke test section).
- On the Mac, Liam's Claude adds `aarch64-apple-darwin` (and `x86_64-apple-darwin` if Intel matters), builds the core as `staticlib` per target from the same commit, `lipo`s if universal, runs `xcodebuild -create-xcframework -library libcore.a -headers Headers -output Core.xcframework`, and wraps it in a SwiftPM package with a `binaryTarget` plus a Swift target holding `core.swift`. Xcode, `xcodebuild`, `lipo` and the Apple SDKs exist only on macOS, so none of this moves to Linux.

`[bindings.swift]` options in `uniffi.toml` that matter here: `module_name`, `ffi_module_name`, `ffi_module_filename`, `omit_argument_labels`, `generate_immutable_records` with `mutable_records`, `generate_codable_conformance`, `custom_types`, `rename`, `omit_checksums`, `link_frameworks`. There is no `experimental_sendable_value_types` option in 0.32.0; `Sendable` conformance is unconditional (see the lifetimes section). Source: https://mozilla.github.io/uniffi-rs/latest/swift/configuration.html.

## Types that cross and types that do not

### Builtins and their Swift shape

The builtin table lists `bool`, `u8` to `i64`, `f32`, `f64`, `String`, `Vec<u8>` (as `bytes`), `SystemTime` (as `timestamp`, "Precision may be lost when converting to Python and Swift types"), `Duration`, `&T` for `&str` and `&[T]` arguments, `&[u8]`, `Box<T>`, `Option<T>`, `Vec<T>`, `HashMap<K, V>`, `HashSet<K>` (proc-macro only), `()` and `Result<T, E>`. Source: https://mozilla.github.io/uniffi-rs/latest/types/builtin_types.html. The Swift names come from the generator: `Bool`, `Int8` to `UInt64`, `Float`, `Double`, `String`, `Data`, `Date`, `TimeInterval`, `T?`, `[T]`, `[K: V]`, `Set<T>`. Source: https://github.com/mozilla/uniffi-rs/blob/main/uniffi_bindgen/src/bindings/swift/gen_swift/primitives.rs, `miscellany.rs` and `compounds.rs` in the same directory, and https://mozilla.github.io/uniffi-rs/latest/swift/overview.html. The smoke test observed `addedAt: Date`, `poster: Data?`, `scores: [String: Double]` and `took: TimeInterval` in the generated struct.

Timestamps and durations cross as seconds plus `UInt32` nanoseconds. A negative `TimeInterval` lowered as a `Duration` traps: `fatalError("Invalid duration, must be non-negative")`. Source: https://github.com/mozilla/uniffi-rs/blob/main/uniffi_bindgen/src/bindings/swift/templates/DurationHelper.swift and `TimestampHelper.swift` beside it.

`HashMap` keys may be any crossable type that is `Hash + Eq` in Rust; the Rust bound is `K: Lower<UT> + std::hash::Hash + Eq`. Source: https://github.com/mozilla/uniffi-rs/blob/main/uniffi_core/src/ffi_converter_impls.rs, and CHANGELOG v0.18.0 "Record types can now contain any hashable type as its key. This is implemented for Kotlin, Python and Swift". The probe on this host compiled `HashMap<u64, String>` and `HashMap<Enum, String>`.

Not supported at all: `u128`, `i128`, `char`, `usize`, `isize`, anonymous tuples, fixed-size arrays, generics, `Rc`, `Cow`, raw pointers, references in return position. None of them appear in the type model (`uniffi_meta/src/types.rs`) or the converter impls. Source: https://github.com/mozilla/uniffi-rs/blob/main/uniffi_meta/src/types.rs and https://github.com/mozilla/uniffi-rs/blob/main/uniffi_core/src/ffi_converter_impls.rs. `u128` has an open ticket: https://github.com/mozilla/uniffi-rs/issues/2691. The probe on this host reproduced each as a compile error: `u128: Lift<UniFfiTag>` not satisfied, likewise `i128`, `usize`, `char`; `(u32, String): LowerReturn<UniFfiTag>` not satisfied; a generic record fails with "cannot find type `T`"; `PathBuf: Lift<UniFfiTag>` not satisfied (bridge it through a custom type).

References: `&str`, `&[T]` and `&Record` are accepted as arguments, and the reference must be visible in the signature (a type alias hiding it is rejected). `&[u8]` is argument only and cannot be nested. Foreign trait methods take no references. Source: https://mozilla.github.io/uniffi-rs/latest/proc_macro/functions.html, https://mozilla.github.io/uniffi-rs/latest/types/bytes.html, and https://mozilla.github.io/uniffi-rs/latest/foreign_traits.html (issue #2263). The probe compiled `&str` and `&[u8]` arguments.

### Records

A record is a struct with named fields and no `&mut` methods, declared with `#[derive(uniffi::Record)]`. Fields "can be of any UniFFI supported type, including objects, vecs, maps and other records"; an object field must be `Arc<T>`; no references or smart pointers other than that. Defaults come from `#[uniffi(default = ...)]` or bare `#[uniffi(default)]`. Source: https://mozilla.github.io/uniffi-rs/latest/types/records.html, https://mozilla.github.io/uniffi-rs/latest/proc_macro/records.html and https://mozilla.github.io/uniffi-rs/latest/types/defaults.html. In Swift a record is a `public struct` with `public var` fields, a memberwise `init`, `Sendable` under `#if compiler(>=6)`, and `Equatable` plus `Hashable` only when it holds no object (source comment referencing #2409). Source: https://github.com/mozilla/uniffi-rs/blob/main/uniffi_bindgen/src/bindings/swift/templates/RecordTemplate.swift and `gen_swift/mod.rs`. Tuple structs are not records (the derive panics on unnamed fields; the probe reproduced "proc-macro derive panicked"); use `uniffi::custom_newtype!` for a one-field wrapper. Source: https://github.com/mozilla/uniffi-rs/blob/main/uniffi_macros/src/record.rs. An empty record `struct Unit {}` compiles (probe).

### Enums

`#[derive(uniffi::Enum)]` accepts fieldless variants, named-field variants and positional variants ("Enums can be very flexible (although UDL doesn't support all of this)"). Source: https://mozilla.github.io/uniffi-rs/latest/types/enumerations.html and the proc-macro fixture's `MixedEnum { None, String(String), Int(i64), Both(String, i64), All { s: String, i: i64 }, Vec(Vec<String>) }` at https://github.com/mozilla/uniffi-rs/blob/main/fixtures/proc-macro/src/lib.rs. The proc-macro enumerations page still says variant fields must be named; the changelog (0.27.0 "Procmacros support tuple-enums"), the fixtures and the probe on this host (a `(String, u32)` variant compiled) contradict it. Variant fields follow the record field rules, so a variant may carry a record, a `Vec` of records, another enum or an `Arc<Object>` (probe: `Got { handle: Arc<Handle> }` compiled). Explicit discriminants need a `#[repr]` to reach Swift, where the enum gains a raw type such as `UInt8`. Source: https://mozilla.github.io/uniffi-rs/latest/proc_macro/enumerations.html.

Swift shape: `public enum` with `case name(field: Type)` for named fields and `case name(Type)` for positional ones, lowerCamel case names, `indirect` when recursive, `Sendable`, `Equatable` and `Hashable` under the same no-object rule. Source: https://github.com/mozilla/uniffi-rs/blob/main/uniffi_bindgen/src/bindings/swift/templates/EnumTemplate.swift. Observed on this host: `case scanLibrary(root: String)`, `case markEpisode(seriesId: UInt64, episode: UInt32)`, `case ping`, and `case scanFinished(series: [Series], took: TimeInterval)`.

### Errors

The error type "must be an `enum` and implement `std::error::Error` (thiserror works!)". Source: https://mozilla.github.io/uniffi-rs/latest/types/errors.html. `#[derive(uniffi::Error)]` exposes variant fields by default; `#[uniffi(flat_error)]` exposes only the variant names with the `Display` string as the single field, which is how a variant can wrap a non-uniffi type such as `reqwest::Error`. Source: https://mozilla.github.io/uniffi-rs/latest/proc_macro/errors.html. A struct cannot be an error enum (probe: "This derive must only be used on enums"); an object can be thrown instead (`Result<T, Arc<MyError>>` or `Result<T, MyError>` since 0.28.0), in which case Swift gets a class conforming to `Swift.Error`. Source: the errors page above. Error variants may hold records (probe) and objects (probe, once the object derives `Debug`).

In Swift the error becomes `public enum E: Swift.Error, Foundation.LocalizedError` (plus `Equatable`, `Hashable` without objects); variant names keep Rust casing (`.NotFound(id:)`), unlike plain enums. A Rust `Result<T, E>` becomes `func f(...) throws -> T`. Source: https://github.com/mozilla/uniffi-rs/blob/main/uniffi_bindgen/src/bindings/swift/templates/ErrorTemplate.swift and https://mozilla.github.io/uniffi-rs/latest/swift/overview.html. A Rust panic is caught by `catch_unwind` on the Rust side and surfaces in Swift as `UniffiInternalError.rustPanic(message)`; in a `throws` function it is catchable as a generic `Error` (the enum is `fileprivate`, so it cannot be matched by case), and in a non-throwing function it is a fatal trap. Source: https://github.com/mozilla/uniffi-rs/blob/main/uniffi_core/src/ffi/rustcalls.rs, https://github.com/mozilla/uniffi-rs/blob/main/uniffi_bindgen/src/bindings/swift/templates/Helpers.swift and the overview page. Rule for the core: every call that can fail returns `Result`, and nothing exported panics on user input.

### Custom types

`uniffi::custom_type!(Name, Bridge)` and `uniffi::custom_newtype!` let any Rust type cross as a bridge type ("Any valid type can be a bridge type"); types from other crates need `remote`. The old `UniffiCustomTypeConverter` trait is gone since 0.29. Source: https://mozilla.github.io/uniffi-rs/latest/types/custom_types.html and https://mozilla.github.io/uniffi-rs/latest/Upgrading.html. Swift sees the bridge type as a `typealias` unless `[bindings.swift.custom_types.Name]` in `uniffi.toml` supplies `type_name`, `imports`, `lift` and `lower`; the shipped example maps `Url` to Foundation `URL`. Source: https://github.com/mozilla/uniffi-rs/blob/main/examples/custom-types/uniffi.toml. This is the route for `PathBuf`, `url::Url`, `uuid::Uuid` and `chrono` types.

### Methods on objects

Methods must take `&self` or `self: Arc<Self>`; `&mut self` is refused ("The Rust struct must not expose any methods that take `&mut self`") and interior mutability must be `Send + Sync`, so `RefCell` is out. Source: https://mozilla.github.io/uniffi-rs/latest/types/interfaces.html and https://github.com/mozilla/uniffi-rs/blob/main/uniffi_macros/src/fnsig.rs. The probe reproduced the failure.

## Async functions, callback interfaces and foreign traits

### Exporting an async function and who polls it

`#[uniffi::export]` on an `async fn` is all the declaration needs; "There's no requirement for a Rust event loop", because "the foreign bindings supply the 'executor'". Source: https://mozilla.github.io/uniffi-rs/latest/futures.html. The internals page says who drives the future: "UniFFI piggybacks off the runtime from the foreign bindings. The generated Rust code schedules work using callbacks provided by the foreign bindings", and "The async Rust code runs in a Future::poll method, inside the foreign event loop. This code never blocks." Source: https://mozilla.github.io/uniffi-rs/latest/internals/async-overview.html. In code, Swift calls the poll function inside `withUnsafeContinuation` on the Swift task's thread, Rust polls the inner future synchronously right there, and a waker firing from any Rust thread invokes the continuation callback on the waking thread; the next poll happens once Swift's executor reschedules the task. Source: https://github.com/mozilla/uniffi-rs/blob/main/uniffi_bindgen/src/bindings/swift/templates/Async.swift, https://github.com/mozilla/uniffi-rs/blob/main/uniffi_core/src/ffi/rustfuture/future.rs and `scheduler.rs` beside it. The future must be `Send` "because the Foreign code may call the `rust_future_*` methods from different threads". Source: https://github.com/mozilla/uniffi-rs/blob/main/uniffi_core/src/ffi/rustfuture/mod.rs.

So an exported future is never polled on a tokio worker unless the core spawns it there. Tokio primitives inside such a future need a tokio context. `#[uniffi::export(async_runtime = "tokio")]` supplies one by wrapping the scaffolding future in `async_compat::Compat`; it accepts only `"tokio"`, requires the `tokio` cargo feature of `uniffi`, refuses non-async functions, and since 0.32.0 also applies to trait exports. Source: https://github.com/mozilla/uniffi-rs/blob/main/uniffi_macros/src/export/scaffolding.rs, https://github.com/mozilla/uniffi-rs/blob/main/uniffi_macros/src/export/attributes.rs, https://github.com/mozilla/uniffi-rs/blob/main/uniffi/Cargo.toml. `Compat` enters the context of a global single-threaded tokio runtime that async-compat creates on demand; "That does not mean the future is polled by the tokio runtime". Source: https://docs.rs/async-compat/latest/async_compat/. The manual never documents the attribute, and the maintainers are unsure about keeping it: "There's also the `uniffi::async_runtime` macro attribute to help with this, but it's not clear if we want to continue to support it (#1726)". Source: https://mozilla.github.io/uniffi-rs/latest/internals/async-overview.html and https://github.com/mozilla/uniffi-rs/issues/1726. A known trap: a synchronous method inside an `async_runtime = "tokio"` impl block that calls `tokio::spawn` panics with "there is no reactor running". Source: https://github.com/mozilla/uniffi-rs/issues/2811.

The route the internals page recommends instead: "Keep a reference to the runtime; Use a bridge function like tokio::Runtime::spawn to await a future that runs in that runtime." Source: https://mozilla.github.io/uniffi-rs/latest/internals/async-overview.html. This matches the map's decision of tokio inside the core behind a synchronous facade: the core owns a `tokio::runtime::Runtime`, a job starts with `self.runtime.spawn(...)` from a synchronous call, and an exported `async fn` that must await core work does `self.runtime.spawn(work).await`, which needs no attribute because a `JoinHandle` polls from any executor. The smoke test ran the job half exactly that way (events emitted from a spawned task) and the async half through the attribute (`tokio::time::sleep` inside `fetch_title`); both worked. "Beware that some Rust crates will present async APIs that silently start up runtimes in the background. For example, reqwest will start a tokio runtime." Source: same page.

Synchronous calls run on the caller's thread: "Swift links to a static library and calls the C functions directly". Source: https://mozilla.github.io/uniffi-rs/latest/internals/rust_calls.html. A synchronous call from SwiftUI's main thread therefore blocks it for as long as the core holds a lock or does I/O, which is the map's "calls return fast" rule stated from the other side.

### How Swift awaits

The generated signature is `func f(...) async throws -> T` (or `async -> T` with `try!` inside when the Rust function cannot fail), implemented by `uniffiRustCallAsync`, which loops on `withUnsafeContinuation` until the poll reports ready and frees the Rust future in a `defer`. Source: https://github.com/mozilla/uniffi-rs/blob/main/uniffi_bindgen/src/bindings/swift/templates/Async.swift and `macros.swift`. The fixture calls it from a plain `Task { let result = await sayAfter(...) }`. Source: https://github.com/mozilla/uniffi-rs/blob/main/fixtures/futures/tests/bindings/test_futures.swift. Observed on this host: `open func fetchTitle(id: UInt64) async throws -> String`, awaited from a `Task`, resumed off the main thread, and its `Err` arrived as a thrown `CoreError.NotFound(id: 2)`.

Cancellation does not cross from Swift. "We don't directly support cancellation in UniFFI even when the underlying platforms do. You should build your cancellation in a separate, library specific channel; for example, exposing a `cancel()` method that sets a flag that the library checks periodically." Source: https://mozilla.github.io/uniffi-rs/latest/futures.html. The Swift template never calls `rust_future_cancel`, and `Helpers.swift` has `case CALL_CANCELLED: fatalError("Cancellation not supported yet")`. Source: https://github.com/mozilla/uniffi-rs/blob/main/uniffi_bindgen/src/bindings/swift/templates/Helpers.swift. The generated file on this host contains no `withTaskCancellationHandler`. A cancelled Swift `Task` keeps waiting for Rust to finish, then drops the future. PR #2887 proposes an opt-in `cancellable` export that maps `Task.cancel()` to a Rust drop; it is open. Source: https://github.com/mozilla/uniffi-rs/pull/2887 and https://github.com/mozilla/uniffi-rs/issues/2771. The working pattern in #2771 is a Rust-side cancel token object called from `withTaskCancellationHandler`. For the core this means every job carries a cancel call, and async calls stay short.

### Callback interfaces versus foreign traits

Callback interfaces (`#[uniffi::export(callback_interface)]`, received as `Box<dyn Trait>`) "are (soft) deprecated, remain now for backwards compatibility, but foreign traits should be preferred". Source: https://mozilla.github.io/uniffi-rs/latest/types/callback_interfaces.html. Foreign traits are `#[uniffi::export(foreign)]` (only the shell implements it) or `#[uniffi::export(rust, foreign)]` (both sides), received as `Arc<dyn Trait>`; `with_foreign` is a deprecated alias since 0.32.0. Source: https://mozilla.github.io/uniffi-rs/latest/proc_macro/traits.html and https://mozilla.github.io/uniffi-rs/latest/foreign_traits.html. Rules for the trait: methods take `&self` (or `self: Arc<Self>`), parameters are passed by value because "references in foreign trait methods aren't supported" (issue #2263), no constructors, and a method should return `Result` if the shell's implementation can fail, "otherwise these errors will panic"; the error type then needs `From<uniffi::UnexpectedUniFFICallbackError>`. Source: https://mozilla.github.io/uniffi-rs/latest/foreign_traits.html. Async methods on foreign traits exist since 0.27.0 ("Trait interfaces can now have async functions, both Rust and foreign-implemented") and the fixture writes them with `#[async_trait::async_trait]` under the export attribute; Rust can `await` a Swift implementation, and dropping the Rust future cancels the Swift `Task`. Source: https://github.com/mozilla/uniffi-rs/blob/main/CHANGELOG.md and https://github.com/mozilla/uniffi-rs/blob/main/fixtures/futures/src/lib.rs. The probe compiled both an async foreign trait method and a `Result`-returning one.

In Swift a foreign trait is `public protocol EventListener: AnyObject, Sendable`, so the implementer must be a class and must be `Sendable`, in practice `final class Listener: EventListener, @unchecked Sendable`. Source: https://github.com/mozilla/uniffi-rs/blob/main/uniffi_bindgen/src/bindings/swift/templates/Protocol.swift, CHANGELOG 0.29.1, and the overview's "your implementation of that protocol must too" at https://mozilla.github.io/uniffi-rs/latest/swift/overview.html. Observed on this host: exactly that protocol line.

### Invoking a foreign trait from a tokio thread

The generated Rust method body is a direct C call through the vtable on whichever thread calls it; nothing dispatches or queues. Source: https://github.com/mozilla/uniffi-rs/blob/main/uniffi_macros/src/export/callback_interface.rs. The documentation states the contract from the other end: "the methods of the foreign class must be safe to call from multiple threads at once, but Rust can not enforce this in the foreign code" and "We insist that all object instances exposed to foreign-language code be `Sync` and `Send`, so that they're safe to access regardless of the threading model of the calling code." Source: https://mozilla.github.io/uniffi-rs/latest/types/callback_interfaces.html and https://mozilla.github.io/uniffi-rs/latest/internals/design_principles.html. The Kotlin chapter shows the tokio case by name: "take tokio for example, and we need to call uniffi's callback in the tokio worker threads". Source: https://mozilla.github.io/uniffi-rs/latest/kotlin/gradle.html. On the Swift side the vtable closure looks the object up in an `NSLock`-guarded handle map and calls the method on the calling thread. Source: https://github.com/mozilla/uniffi-rs/blob/main/uniffi_bindgen/src/bindings/swift/templates/CallbackInterfaceImpl.swift and `HandleMap.swift`. Observed on this host: both events arrived on tokio worker threads with `Thread.isMainThread == false`. The Swift listener must hop to the main actor itself before touching view state; uniffi will never do it.

The listener's lifetime: lowering a Swift object inserts a strong reference into the handle map and hands Rust the key; Rust's `Drop` for the generated handler calls the vtable's free, which removes the entry. "The generated Rust code calls this in the `Drop` implementation for the callback interface." Source: https://mozilla.github.io/uniffi-rs/latest/internals/foreign_calls.html. So the listener lives as long as the core holds its `Arc`, and its `deinit` may run on a tokio thread (inferred from the mechanism, not documented). The foreign traits page warns that a listener holding the core that holds the listener leaks: "UniFFI doesn't try to help here". Source: https://mozilla.github.io/uniffi-rs/latest/foreign_traits.html.

### Event delivery pattern

The manual has no chapter on events, no stream type and no `AsyncSequence`; on streams the maintainers said "There are no such plans" and, more recently, "it might be better to wait until things have standardized more it Rust itself". Source: https://github.com/mozilla/uniffi-rs/issues/1485 and https://github.com/mozilla/uniffi-rs/issues/2755. The documented pattern is to store a foreign trait once: "Rust developers need to declare these traits extending `Send` so they can be stored in Rust, i.e. not passed in as an argument to be used immediately", and the Swift test's comment "This is crucial if we want to configure a system at startup, then use it without passing callbacks all the time." Source: https://github.com/mozilla/uniffi-rs/blob/main/fixtures/callbacks/src/callbacks.udl and https://github.com/mozilla/uniffi-rs/blob/main/fixtures/callbacks/tests/bindings/test_callbacks.swift; the foreign traits page stores `keychain: Arc<dyn Keychain>` the same way. The alternative, an `async fn next_event()` the shell awaits in a loop, is what a user in #2771 ships, and the missing cancellation is exactly their complaint.

Decision this enables: the core exposes `subscribe(listener: Arc<dyn EventListener>)` on a `#[uniffi::export(foreign)] trait EventListener: Send + Sync { fn on_event(&self, event: Event); }`, keeps the listeners in a `Mutex<Vec<...>>`, and fans each event out from the tokio thread that produces it; an unsubscribe call or a subscription object whose drop removes the listener avoids the cycle. This is the shape the smoke test ran. The macOS shell wraps the listener in one `final class ... @unchecked Sendable` that forwards into a `@MainActor` observable model.

## Object lifetimes

### What an object is

"These `interface` objects are live Rust structs behind an `Arc<>` that have a proxy object on the foreign language side". Constructors are `#[uniffi::constructor]` and may return `Self` or `Arc<Self>`; methods take `&self` or `self: Arc<Self>`; objects passed as arguments arrive as `Arc<T>`; an object nested in a record, enum, `Vec` or `Option` must be `Arc<T>`. Source: https://mozilla.github.io/uniffi-rs/latest/types/interfaces.html and https://mozilla.github.io/uniffi-rs/latest/proc_macro/interfaces.html. The `Send + Sync` requirement is stated and enforced: "UniFFI enforces this by requiring that the Rust implementation of an interface be `Sync+Send`, and you will get a compile-time error if your implementation does not satisfy this requirement", and "they must be `Send+Sync` and must be useable without taking any `&mut` references. Typically this will mean that the Rust implementation of an object uses some of Rust's data structures for thread-safe interior mutability, such as a `Mutex` or `RwLock` or the types from `std::atomic`." Source: same interfaces page and https://mozilla.github.io/uniffi-rs/latest/internals/object_references.html. The derive emits `assert_impl_all!(T: Sync, Send)`. Source: https://github.com/mozilla/uniffi-rs/blob/main/uniffi_macros/src/object.rs. Mandatory since 0.11.0; the reasoning is ADR-0004: "the Rust compiler insists that everything wrapped by uniffi is thread-safe - the only question is who manages this thread-safety." Source: https://github.com/mozilla/uniffi-rs/blob/main/docs/adr/0004-only-threadsafe-interfaces.md. The manual mentions `std::sync` locks and atomics only, never `tokio::sync::Mutex`; the todolist example wraps its state in a `RwLock`. Source: https://github.com/mozilla/uniffi-rs/blob/main/examples/todolist/src/lib.rs. A main-thread-only object was requested and refused: "Rust has no concept of a 'main thread'". Source: https://github.com/mozilla/uniffi-rs/issues/2436.

### The Swift side of an object

The generated class is `open class Core: CoreProtocol, @unchecked Sendable` holding a `UInt64` handle, with `uniffiCloneHandle()` and a `deinit` that calls the free function; the protocol is `public protocol CoreProtocol: AnyObject, Sendable`. Source: https://github.com/mozilla/uniffi-rs/blob/main/uniffi_bindgen/src/bindings/swift/templates/ObjectTemplate.swift, `Protocol.swift`, and `conformance_list_for_object` in https://github.com/mozilla/uniffi-rs/blob/main/uniffi_bindgen/src/bindings/swift/gen_swift/mod.rs. Observed on this host, character for character. The class is not `final` (issue #1043 closed without changing that), carries no `ObservableObject` or `@Observable` conformance, and the maintainers' advice for SwiftUI is a wrapper: "write one wrapping model per screen, lets call it ViewModel, which is a class and annotate it with `@Observable` macro ... So you can use UniFFI exported classes (or enums / structs) as stored properties in this ViewModel." Source: https://github.com/mozilla/uniffi-rs/issues/1043 and https://github.com/mozilla/uniffi-rs/issues/2145. Holding one `Core` for the whole app and calling it from any `Task` is the model uniffi is built for.

Handles are raw `Arc` pointers, not a Rust-side map: "The `Arc<>` is lowered into the foreign code using `Arc::into_raw`, casted to a `u64`"; every method call clones the handle (`Arc::increment_strong_count`) and hands that clone to Rust, and free is `Arc::decrement_strong_count`. Source: https://mozilla.github.io/uniffi-rs/latest/internals/object_references.html. Concurrent calls from many foreign threads are the stated assumption: "calls may come from foreign languages on any thread, outside of the control of Rust's ownership system". Source: same page. "Handles must always be `Send` and the objects they reference must always be `Sync`." Source: https://github.com/mozilla/uniffi-rs/blob/main/uniffi_core/src/ffi_converter_traits.rs.

### One long-lived core handle

The manual says nothing about singletons or statics. The closest primary pattern is the todolist example: a `static DEFAULT_LIST: Lazy<RwLock<Option<Arc<TodoList>>>>` read by a free function `get_default_list() -> Option<Arc<TodoList>>` and set from a method taking `self: Arc<Self>`. Source: https://github.com/mozilla/uniffi-rs/blob/main/examples/todolist/src/lib.rs. Returning `Arc<T>` from a free function is normal ("UniFFI supports both Rust functions that wrap the value in an `Arc<>` and ones that don't"), an object can be passed back into Rust as `Arc<T>` and stored inside another object (the coverall fixture keeps `other: Mutex<Option<Arc<Self>>>`). Source: https://mozilla.github.io/uniffi-rs/latest/types/interfaces.html and https://github.com/mozilla/uniffi-rs/blob/main/fixtures/coverall/src/lib.rs. Either shape works for the core: the shell calls the constructor once at start and keeps the instance, or a free function hands out a clone from a `OnceLock`. The constructor keeps the core free of global state and lets the Linux shell build the same `Arc<Core>` inside its cxx-qt object.

### Drop and lifetime

Lifetime is by reference count, never by the Swift reference alone: "UniFFI wraps all object instances in an `Arc` and leverages their reference-count based lifetimes", and the foreign destructor "will only drop their reference and may not drop the Rust object". Source: https://mozilla.github.io/uniffi-rs/latest/internals/object_references.html and https://mozilla.github.io/uniffi-rs/latest/types/interfaces.html. A tokio task holding an `Arc<Core>` clone keeps the core alive after the shell's last reference is gone, and an in-flight call owns its own clone, so a call can never outlive its object. For async methods the Swift side passes a cloned handle into the future and frees the future in a `defer`. Source: https://github.com/mozilla/uniffi-rs/blob/main/uniffi_bindgen/src/bindings/swift/templates/Async.swift. Reference cycles that include Rust objects are not collected; use `Weak<T>`. Source: CHANGELOG 0.12.0 at https://github.com/mozilla/uniffi-rs/blob/main/CHANGELOG.md. Which thread Rust `Drop` runs on after a Swift `deinit` is not documented.

### Traits as interfaces

A trait bound `Send + Sync` can be exported and travels as `Arc<dyn Trait>`; traits have no constructors, so a free function must hand out the instance, and internally it costs a double `Arc` because `*dyn Trait` is a wide pointer. Source: https://mozilla.github.io/uniffi-rs/latest/types/interfaces.html (section "Exposing Traits as interfaces") and https://mozilla.github.io/uniffi-rs/latest/internals/object_references.html. The core does not need this; a concrete `Core` object suffices, and hiding it behind a trait buys nothing on the Swift side.

### Swift 6 strict concurrency

"UniFFI has partial support for Swift 6." "Most generated code will conform to `Sendable`... At time of writing, it is known that async code will not conform. This is being tracked in #2448". Source: https://mozilla.github.io/uniffi-rs/latest/swift/overview.html. What 0.32.0 generates: objects `@unchecked Sendable`, protocols `AnyObject, Sendable`, records, enums and errors `Sendable` under `#if compiler(>=6)` with no option to turn it off (the 0.27.0 `experimental_sendable_value_types` flag was removed by PR #2318 in 0.29.0), the handle map `@unchecked Sendable`, vtable pointers `nonisolated(unsafe)`. Source: https://github.com/mozilla/uniffi-rs/pull/2318 and the templates directory https://github.com/mozilla/uniffi-rs/tree/main/uniffi_bindgen/src/bindings/swift/templates. Open items that affect a macOS app: #2448 (tracking), #2458 (async code under Swift 6 language mode), #2818 (Xcode 26's default `SWIFT_DEFAULT_ACTOR_ISOLATION=MainActor` makes the generated declarations main-actor isolated and they fail to compile; the workaround is to keep that setting off for the module or `sed` in `nonisolated`), #2803 (Swift 6.2 `Data.bytes` name collision). Source: https://github.com/mozilla/uniffi-rs/issues/2448, https://github.com/mozilla/uniffi-rs/issues/2458, https://github.com/mozilla/uniffi-rs/issues/2818, https://github.com/mozilla/uniffi-rs/issues/2803. PR #2943, the fix for the async foreign trait `@Sendable` error (#2929), merged 2026-07-15, after 0.32.0, so it is not in the pinned release. Source: https://github.com/mozilla/uniffi-rs/pull/2943. uniffi's CI compiles the generated Swift in language mode 5. The safe setting for the macOS appendix: the generated file lives in its own SwiftPM target with `swiftLanguageModes: [.v5]` and default isolation left at nonisolated; the app's own targets can use Swift 6.

## Constraints on the call and event enums

uniffi's derives are attributes on the core's own types and nothing more, so `Call` and `Event` stay ordinary Rust enums that any other bridge, and serde for the socket transport, can also read. The rules below are what makes those enums acceptable to uniffi; ticket #3 supplies the cxx-qt half, and the contract ticket #15 merges both.

1. `Call` and `Event` are plain enums with `#[derive(uniffi::Enum)]`; the same derive shape works for every nested enum. Use named fields on every variant (`MarkEpisode { series_id: u64, episode: u32 }`), which Swift renders as labelled associated values (`.markEpisode(seriesId:episode:)`); positional fields compile but lose the labels.
2. Field types come from this closed set: `bool`, `u8` to `u64`, `i8` to `i64`, `f32`, `f64`, `String`, `Vec<u8>`, `SystemTime`, `Duration`, `Option<T>`, `Vec<T>`, `HashMap<K, V>` with `K: Hash + Eq`, records, other enums, error enums, and `Box<T>` for a recursive variant. Nothing else.
3. Never in a variant or record: `usize`, `isize`, `u128`, `i128`, `char`, tuples, fixed arrays, generics, references, `PathBuf`, `Url`, `Uuid`. Counts and sizes are `u64`; ids are `u64` or `String`; paths in calls and events are `String` (a `PathBuf` custom type is possible but adds a bridge for every field; decide once in #15).
4. Records are structs with named fields only; no tuple structs, no newtype ids unless declared with `uniffi::custom_newtype!`. Every record and variant field is owned; no borrowed data.
5. Keep objects (`Arc<T>`) out of `Call` and `Event`. An object field is legal but strips `Equatable` and `Hashable` from the Swift enum and drags a live handle through the event log and the socket. Events describe facts with plain data; calls name things by id.
6. `Event` derives `Clone` (and `Debug`), because the core fans one event out to every subscribed shell by value. `Call` derives `Clone` and `Debug` for logging.
7. Time crosses as `SystemTime` (Swift `Date`) and spans as `Duration` (Swift `TimeInterval`); a duration is never negative. A tick's position is a `Duration` or an `f64` of seconds; pick one in #15 and keep it.
8. Errors are one `#[derive(uniffi::Error)]` enum, `CoreError`, with named-field variants over the same closed set; third-party errors arrive as a `message: String` field or through `#[uniffi(flat_error)]`. Every call that can fail returns `Result<_, CoreError>`; no exported code panics on shell input, because a panic is a fatal trap in a non-throwing Swift function.
9. The dispatch surface is an object: `#[derive(uniffi::Object)] struct Core` behind `Arc`, `Send + Sync`, `&self` methods only, state under `std::sync` locks or atomics held briefly. Calls return fast; anything longer is a job started with `Runtime::spawn` on the core's own tokio runtime and reported through events.
10. Events leave the core through `#[uniffi::export(foreign)] trait EventListener: Send + Sync { fn on_event(&self, event: Event); }`, registered once by `subscribe`, paired with an unsubscribe. The core calls it on whatever tokio thread produces the event, by value, with no references in the signature; the shell owns the hop to its main thread.
11. Exported async functions are few and short; none relies on Swift cancellation. Every job has a cancel call and a job id in its events.
12. No `#[cfg(target_os = ...)]` on any exported item, because the Swift bindings are generated from the Linux build and would silently lose the gated items.
13. Bindings and library always come from the same commit and the same pinned uniffi version (0.32.0 now); the checksum check refuses anything else at load time.
